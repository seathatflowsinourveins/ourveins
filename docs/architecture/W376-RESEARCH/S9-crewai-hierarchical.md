## §1 CrewAI Architecture Overview — Crew + Agent + Task + Process model

CrewAI is a multi-agent orchestration framework built on four core primitives:

- **`Crew`** (`lib/crewai/src/crewai/crew.py:136-205`) — the top-level orchestrator. Holds `agents: List[BaseAgent]`, `tasks: List[Task]`, and `process: Process`. Entry point is `kickoff(inputs) -> CrewOutput`.
- **`BaseAgent`** (`lib/crewai/src/crewai/agents/agent_builder/base_agent.py:73-121`) — abstract base for agents. Concrete impl is `Agent`. Carries `role`, `goal`, `backstory`, plus `execute_task(task, context) -> str`.
- **`Task`** (`lib/crewai/src/crewai/task.py:87-110`) — a unit of work with `description`, `expected_output`, assigned `agent`, optional `tools`, `output_pydantic`, `output_json`, `guardrail`, `context` (list of upstream tasks).
- **`Process`** (`lib/crewai/src/crewai/process.py:7-13`) — `Enum` with two members: `sequential` and `hierarchical`. (A `consensual` member is documented as future work but not implemented.)

Relationship cardinality: one `Crew` coordinates many `BaseAgent` + executes many `Task` + uses exactly one `Process`. Each `Task` is assigned to one `BaseAgent` (or, under hierarchical, assigned implicitly to the manager who then delegates).

## §2 Hierarchical Process — Manager + Worker Agents, Delegation

Enabled by setting `Crew(process=Process.hierarchical, manager_llm=... | manager_agent=...)`. Exactly one of `manager_llm` or `manager_agent` is required.

**Manager creation**: if no `manager_agent` is supplied, CrewAI auto-creates one from `manager_llm` using predefined role/goal/backstory from translation files. The manager is always initialized with `allow_delegation=True` and equipped with `AgentTools`.

**Entry point**: `Crew._run_hierarchical_process` orchestrates execution.

**Per-task wiring**:
- `_get_agent_to_use` returns the `manager_agent` as the task executor (not the originally-named agent — under hierarchical, task `agent` assignments may be omitted).
- `_prepare_tools` adds delegation tools to the manager when `allow_delegation=True`.
- `_update_manager_tools` injects per-coworker delegation tools so the manager can route to any agent in the crew.

**Delegation tools** (dynamically generated by `AgentTools`):
- `delegate_work_to_coworker(coworker, task, context)` — manager hands a task to a worker. Tool description explicitly mandates passing FULL context because "the coworker knows nothing about the task".
- `ask_question_to_coworker(coworker, question, context)` — manager queries a worker for input.

This is the canonical Anthropic "orchestrator-workers" pattern: manager plans + delegates + validates; workers execute scoped subtasks.

## §3 Sequential vs Hierarchical Process Differences

| Dimension | Sequential | Hierarchical |
|---|---|---|
| Task order | Pre-defined linear list | Dynamic, manager-decided |
| Agent assignment | Each `Task.agent` is pre-bound | Manager allocates at runtime |
| Context flow | Task N output → Task N+1 context (via `Task.context` list) | Manager controls context propagation per delegation |
| Required config | none beyond `agents` + `tasks` | `manager_llm` OR `manager_agent` REQUIRED |
| Best for | Deterministic pipelines (research → write → review) | Open-ended goals requiring planning + adaptive routing |
| Overhead | Low — direct execution | Higher — manager LLM call per delegation decision |

Sequential is the deterministic "pipeline" topology; hierarchical is the "managed team" topology with runtime decomposition.

## §4 Tool Model — BaseTool Subclass Contract, How Tools Are Bound to Agents

**BaseTool contract** (abstract base):
- `name: str` — unique tool identifier shown to the LLM
- `description: str` — when/why/how to use (LLM's selection signal)
- `args_schema: Type[BaseModel]` — Pydantic schema for tool args; auto-generated from `_run` signature if omitted
- `_run(self, **kwargs) -> str` — REQUIRED sync impl
- `_arun(self, **kwargs) -> str` — optional async impl

Example:
```python
class MyCustomTool(BaseTool):
    name: str = "Name of my tool"
    description: str = "What this tool does. Vital for effective utilization."
    args_schema: Type[BaseModel] = MyToolInput
    def _run(self, argument: str) -> str:
        return "Tool's result"
```

Alternative: `@tool` decorator on a plain function.

**Tool binding levels** (two-tier with override semantics):
1. **Per-agent tools**: `Agent(tools=[...])` — available for every task that agent executes.
2. **Per-task tools**: `Task(tools=[...])` — for THAT task, OVERRIDES the agent's tools entirely. Agent's original tool set is unchanged outside this task.

This override semantic is important: per-task tools provide fine-grained capability scoping without mutating agent identity.

## §5 Expected Output Schema Mandate — Structured Worker Output Enforcement

This is the pattern cited in the **parallel-dispatch-mandate** skill: CrewAI's `Task` enforces structured worker output via three layered attributes:

1. **`expected_output: str`** — natural-language description of the expected result. Guides the LLM but is NOT programmatically enforced.
2. **`output_pydantic: Type[BaseModel]`** — Pydantic model the agent's final response MUST conform to. Yields a Pydantic instance.
3. **`output_json: Type[BaseModel]`** — Pydantic model used to produce a JSON dict output conforming to the schema.

**Mutual exclusion**: only ONE of `output_pydantic` / `output_json` may be set per task (validated at Task construction).

**Validation flow** (`_execute_core` sync / `_aexecute_core` async):
- If the agent's raw result is already a `BaseModel` instance → used directly for `pydantic_output` or `json_output`.
- For LLMs supporting native structured output (Bedrock, Gemini, OpenAI strict mode), CrewAI injects a `STRUCTURED_OUTPUT_TOOL_NAME` pseudo-tool into the LLM's tool config. The pseudo-tool's `args_schema` is the target Pydantic model. The `generate_model_description` utility converts the Pydantic model to JSON schema for the LLM.
- `GeminiCompletion` (and provider-equivalents) check the LLM response for the structured-output function call, extract args, and route through `response_model` (which mirrors `output_pydantic`/`output_json`).

**Why this matters for W376**: parent orchestrators dispatching parallel subagents need a guarantee that each worker returns parseable structured output. Without `output_pydantic`/`output_json` (or an equivalent), workers may return free-form text the parent cannot mechanically merge — this is the W376 OpenHands L1/L2/L3 layered-review failure mode and the citation reason in `parallel-dispatch-mandate`.

## §6 Memory + Context Management Across Crew Steps

**Unified Memory** (current implementation — replaces legacy split memory types):
- Single `Memory` class with LLM-driven analysis. Self-organizes by scope, category, and importance.
- Adaptive recall: semantic similarity + recency + importance scoring.
- Legacy taxonomy still documented (short-term, long-term, entity, contextual) but consolidated under one API.

**Save path** (`CrewAgentExecutorMixin._save_to_memory`):
- After each task, the crew extracts discrete facts from task output and writes them with hierarchical scope keys like `/crew/research-crew/agent/researcher`.
- Stored fields: task description, agent role, expected result, actual result.

**Recall path** (`Agent._retrieve_memory_context`):
- Before agent executes a task, query unified memory using the task description.
- Retrieved memories are formatted and prepended to the task prompt.

**Inter-task context (without memory)**: `Task.context: List[Task]` — declares upstream tasks whose outputs are injected as context into the current task's prompt. This is the sequential-pipeline pattern.

Under hierarchical, the manager's delegation tool argument (`context`) is the explicit channel for context handoff (per §2 — tool description mandates manager pass FULL context).

## §7 Error Handling + Retry Within a Crew

**Task-level retry**: `Task.max_retries` is **deprecated**. Replaced by `guardrail_max_retries` — controls retries when a `guardrail` validation function rejects the agent's output.

**Agent-level retry**: governed by `Agent.max_retry_limit`. Two-layer impl:
1. **`_check_execution_error`** — decides whether to re-raise immediately or attempt retry. Re-raises `litellm` exceptions + passthrough exceptions verbatim. Re-raises also when attempt count > `max_retry_limit`.
2. **`_handle_execution_error`** (sync) / `_handle_execution_error_async` (async) — on exception, calls `_check_execution_error`; if retry allowed, recursively calls `execute_task` to re-attempt.

**`LiteAgent._execute_core`** — orchestrates execution. Calls `_invoke_loop`. After execution, if memory enabled, persists output via `_save_to_memory`. Retry loop lives in `_handle_execution_error`, not `_execute_core` itself.

**Guardrails**: `Task.guardrail: Callable` — synchronous output validator. On rejection, agent retries up to `guardrail_max_retries`. Modern replacement for `max_retries`.

## §8 Comparison with W376 OpenHands L1/L2/L3 Layered Review

| Dimension | CrewAI Hierarchical | OpenHands L1/L2/L3 |
|---|---|---|
| Topology | Manager + worker fan-out | Linear review chain (L1 → L2 → L3) |
| Decomposition | Runtime (manager LLM decides) | Compile-time (layer roles fixed) |
| Worker output contract | `output_pydantic` / `output_json` mandatory for parseable merge | Free-form text passed up — no structured schema mandate |
| Delegation primitive | `delegate_work_to_coworker` tool call | Direct subprocess invocation per layer |
| Retry | `guardrail_max_retries` + `max_retry_limit` two-layer | Layer-specific, ad-hoc |
| Context handoff | Tool arg + unified memory recall | Layer-N stdout → Layer-(N+1) stdin |
| Parallel fan-out | Yes (manager can delegate to multiple workers via repeated tool calls) | No — strictly serial up the chain |
| Self-organization | Manager re-plans on partial failures | Each layer escalates only |

**Key gap W376 should close**: OpenHands lacks the `expected_output` + `output_pydantic` schema mandate. CrewAI's structured-output enforcement is the missing ingredient for reliable parallel-subagent merge (matches what `parallel-dispatch-mandate` skill calls out).

## §10 Applicable Patterns for W376 (or W377+)

Patterns CrewAI does well that W376 should adopt:

1. **Structured output mandate on subagent tasks** — adopt CrewAI's `output_pydantic`/`output_json` pattern for W376 subagent dispatches. Every parallel subagent should return JSON conforming to a parent-defined Pydantic schema, NOT free-form markdown. This is the missing piece in OpenHands L1/L2/L3.

2. **Manager-with-delegation-tools topology** — for hierarchical reviews, model the parent orchestrator as a manager LLM equipped with `delegate_to_subagent(name, task, context)` tool. Forces explicit context-passing (mirrors CrewAI's "coworker knows nothing about the task" mandate). Maps cleanly to Claude Code's `Agent` tool.

3. **Two-tier tool binding (per-agent vs per-task)** — useful for W376 subagent_type allowlist + per-dispatch tool scoping. Per-task tools override per-agent defaults without mutating agent identity.

4. **Guardrails over retry-count** — `guardrail: Callable` + `guardrail_max_retries` is more semantic than blind retry. W376 should add output-validation guardrails on subagent results (e.g., "non-empty final message" matches the `empty-final-message-guard` skill at Δ-G49).

5. **Hierarchical scope keys for cross-session memory** — adopt `/crew/<name>/agent/<role>` style for T6 basic-memory wave-thread keys to improve recall granularity.

6. **Manager auto-equipped with `allow_delegation=True`** — in W377 orchestrator-mode, auto-inject delegation tools rather than requiring the parent prompt to declare them. Reduces orchestrator prompt-engineering burden.

7. **Mutual exclusion validators on Task** — `output_pydantic` vs `output_json` are mutually exclusive, validated at construction. W376 task-spec schema should adopt same pattern for conflicting fields.

8. **`expected_output` natural-language contract paired with schema** — provide BOTH a human-readable expected_output AND a Pydantic schema. Belt-and-suspenders: LLM gets prose guidance + tool-call schema enforcement.

Patterns to AVOID importing wholesale:
- CrewAI's deprecated `max_retries` (replaced by guardrail-based) — adopt the modern guardrail pattern from day 1, skip the legacy migration step.
- CrewAI's auto-created manager from `manager_llm` is convenient but obscures manager prompt-engineering — W376 should require explicit manager agent spec for auditability.
