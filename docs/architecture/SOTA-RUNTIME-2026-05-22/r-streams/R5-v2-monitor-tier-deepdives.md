## §1.1 rcortx/kiwiq (1,032★)
- **Dispatch shape**: FastAPI REST server on port 8000 (`uvicorn kiwi_app.main:app`). Dispatch via HTTP API — `/docs` exposes OpenAPI. NOT a CLI runtime; you POST to the FastAPI app and receive WebSocket-streamed progress events. Workflows are predefined Python/JSON graph schemas compiled to LangGraph + executed via Prefect worker.
- **Architecture depth**: Heavyweight orchestration stack — FastAPI + LangGraph + Prefect + PostgreSQL (state/checkpoints) + MongoDB (versioned customer docs) + Weaviate (vector RAG) + Redis (cache) + RabbitMQ (event bus). 24+ reusable node types (LLM, routing, conditional, transforms, scraping, code-runner, sub-workflows, HITL). 27+ shipped workflow definitions across Content Studio (11) + Diagnostics (10) + Sales/Investor (2) + Playbooks (2) + Labs (3). Multi-provider LLM (OpenAI/Anthropic/Gemini/Perplexity/Fireworks/Bedrock). HITL via WebSocket streaming.
- **Production evidence (verified)**: README claims "powered KiwiQ AI (Marketing AI Agents) in production". Repository ships 75+ unit/integration tests + 40+ pages of design docs (`docs/design_docs/workflow_service_docs/workflow_builder_guides/`). `docker-compose.prod.yml` exists with Nginx+Certbot SSL, external managed DBs, resource limits, JSON-file log rotation, health checks, tuned for 4x concurrent workflow execution. "Battle-tested on 200+ enterprise AI agents" is the README's self-claim — the 27 shipped workflows + prod docker-compose corroborate non-trivial production use, but the 200+ figure is unverifiable from public artifacts.
- **Is it autonomous runtime?**: **NO — workflow orchestration platform, not an autonomous-runtime peer to OpenHands/Letta**. KiwiQ executes predefined LangGraph DAGs (deterministic node-graph schemas), not autonomous perceive-decide-act loops with self-directed task selection. HITL nodes explicitly pause for human input. This is closer to a "workflow engine + LangGraph + Prefect" hosted as a SaaS-shaped FastAPI service. The CC orchestrator would dispatch to a *predefined workflow*, not "build me a feature autonomously."
- **sca-v18 tier**: **KEEP-MONITOR (lean toward DEMOTE-TO-BLOCK for autonomous-runtime category)**. Reasoning: not a true autonomous runtime, but a credible workflow-orchestration platform — could re-enter consideration if scope expands to "workflow-orchestration" category. For the v2 SOTA autonomous-runtime evaluation, it's MISCATEGORIZED.
- **Confidence**: HIGH (README is 18KB, architecture diagram explicit, license Apache-2.0 verified, deployment docs concrete)

## §1.2 open-multi-agent/open-multi-agent (6,224★)
- **Dispatch shape**: **npm LIBRARY** (`npm install @open-multi-agent/core`) + optional `oma` CLI binary for shell/CI. Primary dispatch is `import { OpenMultiAgent } from '@open-multi-agent/core'` → `new OpenMultiAgent({...}).runTeam(team, 'goal string')`. CC would dispatch by either (a) writing a small TS driver script that imports the library and invokes `runTeam`, or (b) shelling out to `oma` JSON-first CLI. NOT a CLI subprocess in the OpenHands/Codex sense, NOT a REST server out of the box, NOT an MCP server. Three runtime dependencies — drops into any Node.js backend.
- **Architecture depth**: Coordinator agent decomposes goal → task DAG at runtime → parallelizes independents → synthesizes result. Three modes: `runAgent()` (single), `runTeam(team, goal)` (auto-orchestrated coordinator), `runTasks(graph)` (explicit). 10 built-in LLM adapters (Anthropic, OpenAI, Azure, Bedrock, Gemini, Grok, DeepSeek, MiniMax, Qiniu, Copilot) + OpenAI-compatible (Ollama/vLLM/LM Studio/llama.cpp/OpenRouter/Groq/Mistral) + Vercel AI SDK passthrough. 6 built-in tools (`bash`, `file_*`, `grep`, `glob`) + opt-in `delegate_to_agent` + custom via `defineTool() + Zod` + stdio MCP via `connectMCPTools()`. Pluggable `MemoryStore` (default in-process KV; Redis/Postgres/Engram). Architecture diagram shows: `OpenMultiAgent` orchestrator → Team (AgentConfig[]+MessageBus+TaskQueue+SharedMemory) → AgentPool (Semaphore+runParallel) + TaskQueue (dependency graph+auto-unblock+cascade-failure) → Agent (run/prompt/stream) → LLMAdapter + AgentRunner → ToolRegistry. Production controls: `maxTurns`, `contextStrategy` (sliding-window/summarize/compact/custom), `maxToolOutputChars`, per-task `maxRetries`/`retryDelayMs`/`retryBackoff`, `maxTokenBudget`, `loopDetection` with `onLoopDetected: 'terminate'`, `onTrace` spans, `renderTeamRunDashboard(result)`.
- **Production evidence (verified)**: Codecov badge + CI badge + npm version badge. Launched 2026-04-01 under MIT. ONE confirmed production user listed in README: `temodar-agent` (~60 stars) — WordPress security analysis platform by Ali Sünbül, Docker runtime. README acknowledges "Using OMA in production? Open a discussion and we will list it here" (single listing as of fetch). Integrations: Engram (memory sync), @agentsonar/oma (cycle detection sidecar). Featured-partner program documented. Multiple `examples/cookbook/` end-to-end workflows shipped (contract-review-dag, meeting-summarizer, competitive-monitoring, translation-backtranslation). 6,224★ figure is high but launched 2026-04-01 = ~7 weeks old at time of evaluation → star-velocity is the indicator, not maturity.
- **Is it autonomous runtime?**: **PARTIAL — autonomous task-DAG decomposer, but library-shaped not runtime-shaped**. The coordinator pattern (`runTeam(team, goal)`) does decompose a goal into a task DAG autonomously and execute it. However, it's still a library you embed in your own Node.js process — there's no standalone runtime daemon you dispatch to and walk away from. The "perceive-decide-act" loop happens *inside* `runTeam()` call, then returns. It's closer to "LangGraph-but-goal-driven-instead-of-graph-first" than to OpenHands/Letta's daemon-shape. CC dispatch model: spawn a TS process that calls `runTeam` and tail its output.
- **sca-v18 tier**: **PROMOTE-FROM-MONITOR-TO-CONSIDER (with caveat)**. Reasoning: the library has substantive autonomous-decomposition primitive (coordinator pattern), strong production-controls (retry/budget/loop-detection/context-strategy), broad provider matrix (10 built-in + Vercel AI SDK pass-through), MIT license, mature TypeScript ecosystem. **CAVEAT**: only 1 confirmed production user + ~7 weeks old + 6,224★ velocity is suspiciously high for a 7-week-old repo (worth manual star-velocity sanity check). For TypeScript-stack projects this is a credible candidate; for Python-stack (this runtime) the embed-in-Node-process model is a poor fit.
- **Confidence**: MEDIUM-HIGH (README extensive 24KB, npm package exists, architecture diagram concrete, 10 LLM adapters listed by contributor names — but only 1 production user listed)
- **Citation**: GitHub README `open-multi-agent/open-multi-agent/blob/main/README.md` (sha ae542ec25dc1, 24,399 bytes, fetched 2026-05-22 via `mcp__github__get_file_contents`). npm package `@open-multi-agent/core` exists per shields.io badge. ## §1.3 salesforce/agentscript (233★)
- **Dispatch shape**: **NOT A RUNTIME — it is a language/DSL + config-schema + COMPILER**. Indentation-based DSL (YAML/Python-like syntax) compiled via `@agentscript/compiler` package + `agentforce` CLI `compile` subcommand into a Salesforce-runtime-specific JSON/YAML spec. Dispatch entry point in the DSL is the `start_agent` block (singular per file). External orchestrators consume the COMPILED OUTPUT, not the AgentScript source. No way for CC to "dispatch a task" — there's no execution surface. CC could only invoke `agentforce compile` to convert `.agent` → Salesforce runtime spec, then hand spec to Agentforce platform (separate Salesforce SaaS product).
- **Architecture depth**: Core blocks: `system`, `config`, `variables`, `start_agent`, `subagent`. Extensible "dialect" system — base AgentScript dialect defines core constructs; Agentforce dialect extends with Salesforce-platform-specific features. Action targets like `"flow://Flow_API_Name"` are resolved by the *consuming runtime*, not by AgentScript. Reasoning blocks contain LLM instructions + actions; actions can be `@utils.transition to @subagent.X` for state-machine-style routing between sub-agents.
- **Production evidence (verified)**: 233★ — low. Created 2026-04-13. Salesforce corporate-backed. Designed for Salesforce Agentforce platform consumption. NO releases tagged yet per evaluation metadata. Production evidence is limited to Salesforce-internal Agentforce usage (not publicly verifiable from this repo alone).
- **Is it autonomous runtime?**: **NO — explicitly NOT a runtime per deepwiki authoritative answer**. Quote: "AgentScript is primarily a language/DSL and a config-schema, not a runtime itself." It is the *agent definition language*; Salesforce Agentforce is the runtime that consumes it.
- **sca-v18 tier**: **DEMOTE-TO-BLOCK for autonomous-runtime category**. Reasoning: definitively miscategorized in the MONITOR-tier autonomous-runtime evaluation. AgentScript would be relevant under a "agent-config-DSL" or "schema-driven agent definition" category (where it competes with PromptFlow YAML, Mastra workflows, LangSmith templates). For the v2 SOTA autonomous-runtime evaluation, this is a BLOCK-tier wrong-category candidate. If CC ever needed to integrate with Salesforce Agentforce specifically, agentscript would be relevant — but as a *config primitive*, not a runtime.
- **Confidence**: HIGH (deepwiki gave authoritative architecture-level answer; quote: "AgentScript itself does not directly execute tasks; instead, it compiles `.agent` files into a Salesforce runtime specification")
- **Citation**: deepwiki ask_question response 2026-05-22 (deepwiki search URL: https://deepwiki.com/search/is-salesforceagentscript-a-run_3cf546a7-3bd3-4171-87df-c9c963d53678). Key quote: "External orchestrator would interact with the compiled output, not directly with the AgentScript source." Concrete `start_agent topic_selector` code example provided in deepwiki response.

## §1.4 microsoft/agent-governance-toolkit (1,824★)
- **Dispatch shape**: **MIDDLEWARE / SDK / CLI / MCP-Gateway — multi-surface governance layer, NOT a runtime**. Available as SDK in Python (`pip install agent-governance-toolkit[full]`), TypeScript, .NET, Rust, Go. Unified `agt` CLI for OWASP-compliance verification, installation checks, agent red-teaming. Native middleware/adapter integration with Microsoft Agent Framework, Semantic Kernel, LangChain, AutoGen, LlamaIndex, CrewAI, OpenAI Agents, Google ADK. Also supports MCP Server gateway mode for policy enforcement on MCP tool calls. The toolkit's `StatelessKernel.execute(action, params, context)` is the action-evaluation entry point; the actual *runtime* perceive-act loop is owned by the wrapped framework (AutoGen, LangChain, etc.).
- **Architecture depth**: OS-inspired architecture — kernel + capability model + process isolation + audit logging. Core abstractions: `StatelessKernel` (action evaluator), `ExecutionContext` (agent_id + policies), `PolicyEvaluator` with `PolicyDocument`/`PolicyRule`/`PolicyCondition`/`PolicyAction`/`PolicyOperator`/`PolicyDefaults`, `ExecutionRing` (Ring 0 privilege tiers), `ExecutionSandbox` (blocks dangerous modules + built-ins), `MCPGateway` (tool allow-list enforcement). Operates at the "Agent Action Layer" (what agents *do*) — explicitly distinct from "LLM Output Layer" tools like NeMo Guardrails / Guardrails AI (what LLMs *say*).
- **Production evidence (verified)**: 1,824★, Microsoft corporate-backed, MIT license, v3.7.0 released 2026-05-18 (per evaluation metadata — tagged release evidence). Designed for framework-agnostic integration with 8+ named agent runtimes. OWASP Agentic Top 10 mapping is concrete: ASI-01 (Goal Hijack) → policy-based action interception, ASI-02 (Tool Misuse) → capability-based security + `MCPGateway` allow-list, ASI-05 (Code Execution) → `ExecutionRing` + `ExecutionSandbox`. Cross-framework adapter design is explicit.
- **Is it autonomous runtime?**: **NO — explicitly a governance/policy/sandboxing LAYER per deepwiki authoritative answer**. Quote: "The microsoft/agent-governance-toolkit is a governance, policy, and sandboxing layer that wraps other runtimes, rather than being an autonomous perceive-act loop itself." It does NOT replace runtimes; it intercepts their actions for policy enforcement.
- **sca-v18 tier**: **DEMOTE-TO-BLOCK for autonomous-runtime category BUT PROMOTE-TO-CONSIDER for security-layer category**. Reasoning: definitively NOT a runtime per deepwiki. However, the toolkit is highly relevant for *protecting* whichever autonomous runtime CC ends up integrating — covers all 10 OWASP Agentic Top 10 controls, Microsoft-backed, multi-language SDKs, MCP-gateway-aware. For the v2 SOTA autonomous-runtime evaluation it is wrong-category, but it should be **flagged for follow-up evaluation in a hardening/security-wrapper category** once a runtime is selected. Cardinal-rule-5 alignment: this is the kind of policy-layer that complements Claude Code's OS-sandbox safety boundaries.
- **Confidence**: HIGH (deepwiki returned authoritative architecture-level answer + concrete OWASP-ASI-01/02/05 code examples + dispatch-mode enumeration)
- **Citation**: deepwiki ask_question response 2026-05-22 (deepwiki search URL: https://deepwiki.com/search/is-microsoftagentgovernancetoo_ee62a207-8d3c-44d7-881b-761986bbdbc6). Key quotes: (a) "governance, policy, and sandboxing layer that wraps other runtimes"; (b) "intercepting and governing agent actions *before* execution"; (c) "framework-agnostic and integrates with various agent frameworks". Concrete Python code examples for `StatelessKernel`, `PolicyEvaluator`, `ExecutionRing` provided in deepwiki response.
