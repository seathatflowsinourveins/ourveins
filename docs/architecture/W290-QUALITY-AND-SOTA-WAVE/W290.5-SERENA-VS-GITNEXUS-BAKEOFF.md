## §0 — TL;DR + recommendation

**Recommendation: KEEP BOTH with explicit role split AND a P0 maintenance task to fix each.** Do NOT remove either today.

Three-paragraph defence:

**Paragraph 1 — Serena is genuinely good, but mis-configured right now.** Serena is MIT-licensed (deepwiki-verified from `LICENSE` file line 1; SPDX `MIT`), SHA-pinned to `249f6b07f9ccac259b0ff95e06c9a40629748e17` (strongest supply-chain form per CR-9), local-LSP-only (no network reach — F2 security GREEN), and bundles symbol-level code-intel that **gitnexus simply does not provide** (`find_symbol`, `replace_symbol_body`, `rename_symbol`, `insert_after_symbol`, `find_referencing_symbols`, `get_diagnostics_for_file`). On this runtime, however, the auto-language-detector activated the project as **`rust`-only** because the workspace contains `.cargo/git/checkouts/` (cargo dep cache), so serena REFUSES to read Python files (`Cannot extract symbols from file harness/eval_harness.py. Active languages: ['rust']`). The fix is a 1-line edit to `.serena/project.yml` (force `python` + `rust`) — not a serena defect, an in-runtime mis-config.

**Paragraph 2 — Gitnexus is structurally weaker AND operationally stale.** Gitnexus carries a **PolyForm Noncommercial 1.0.0** license (W259v15 verified verbatim) — under sca-v3 D1 license_compatibility, that's a `1` (NC blocks INSTALL via hard-cap `D1<3` — operator's "stars not hardgate" mandate honoured, but a license-NC IS an INSTALL-tier blocker; it's still PATTERN-STUDY/VENDOR-FORK eligible). It runs on an `npm gitnexus@1.6.4-rc.112` **RC channel** (7.2 RCs/day per W132 audit), and its on-disk index is **368 commits BEHIND** the current main branch HEAD (`892753742d…` indexed 2026-05-13 vs current HEAD 5 days newer). Live probe `mcp__gitnexus__context name=main` returned `Symbol 'main' not found` — because the function was added/renamed after 2026-05-13. Live probe `mcp__gitnexus__query` worked but with `wall=1011.8ms` (1+ second per query), and the symbols it returned were OLD (`evals/evolve_pass_rate_gate.py:main` instead of the present-day `harness/eval_harness.py:main`).

**Paragraph 3 — They serve DIFFERENT non-overlapping code-intel needs.** Serena = **symbol-level LSP code-intel** (per-symbol find/replace/refactor, type diagnostics, symbol-tree navigation). Gitnexus = **graph-level execution-flow code-intel** (blast-radius impact analysis, multi-symbol process tracing, route/API-handler topology, cross-repo group queries). The capability-parity table in §1 confirms only 3-of-21 serena tools have a meaningful gitnexus equivalent, and only 2-of-13 gitnexus tools have a meaningful serena equivalent. **D10 duplication is moderate, not high** — they overlap on basic symbol-search but diverge on what they let you DO with the result. Removing either creates a real capability gap.

**Net**: keep both. Open 2 P0 maintenance items: (i) fix serena project language config; (ii) `gitnexus analyze` re-index to current HEAD. If you cannot fix EITHER, drop gitnexus first (license + staleness + slower = harder to defend than a 1-line YAML fix on serena).

## §2 — Real-task bake-off (3 tasks, both tools each)

### Task A — "find all references to function `main` in `harness/eval_harness.py`" (LSP-style symbol search)

- **Serena** `find_symbol name_path_pattern="run_inspect_lane" relative_path="harness/eval_harness.py"` → **FAILED** (empty result `"[]"`). Root cause: `mcp__serena__get_symbols_overview harness/eval_harness.py` returned `Error: Cannot extract symbols from file harness/eval_harness.py. Active languages: ['rust']`. Serena's auto-language-detection misclassified the project as Rust-only because `.cargo/git/checkouts/` exists in the tree (transitive cargo dep cache). **Not a serena defect — an in-runtime mis-config.** Fix: edit `.serena/project.yml` to include `python` in the language list.
- **Gitnexus** `context name="main" file_path="harness/eval_harness.py"` → **FAILED** (`"error": "Symbol 'main' not found"`). Root cause: gitnexus index `lastCommit 892753742d…` indexed 2026-05-13 is **368 commits behind HEAD**. The `harness/eval_harness.py:main` symbol (line 679 confirmed by grep) was added/renamed after the index was built.
- **Winner**: **Neither**. Both have addressable operational defects. With fixes applied (serena: 1-line YAML; gitnexus: `gitnexus analyze` re-index, ~30s wall), both would succeed.

### Task B — "high-level overview of the harness module"

- **Serena** `get_symbols_overview relative_path="harness/eval_harness.py"` → **FAILED** (same Rust-only mis-config).
- **Gitnexus** `query goal="harness module overview" query="eval harness inspect" limit=3 repo="claude-sota-installed"` → **PARTIAL SUCCESS**: returned 3 processes (`proc_22/23/24_main` — "Main → Parse_codex_verdicts/Load_baseline/Write_baseline"), but the symbols cited were from `evals/evolve_pass_rate_gate.py` not `harness/eval_harness.py`. **Stale-index leakage**: the query SEMANTICALLY matched but the symbol-resolution layer returned outdated symbol locations. Wall-time `1011.8ms` for the query.
- **Winner**: **Gitnexus by default** (returned SOMETHING when serena returned nothing), but the result was misleading due to staleness. With re-index, gitnexus would be strictly better at this query class — process-level summarisation is its signature capability.

### Task C — "blast radius of changing `harness/eval_harness.py::main`"

- **Serena** `find_referencing_symbols name_path="main" relative_path="harness/eval_harness.py"` → not attempted (would fail same mis-config).
- **Gitnexus** `impact target="main" direction="upstream" file_path="harness/eval_harness.py" maxDepth=2` → **FAILED** (`"error": "Target 'main' not found"`). Same staleness root cause.
- **Winner**: **Neither** today; **gitnexus by signature** (blast-radius is its T1-marketing-claim and serena has no graph-level equivalent). With re-index, gitnexus would win this task class outright.

## §6 — Recommendation (THE answer to operator's question)

### "Is serena really good?"

**YES — CONDITIONAL on a 1-line config fix**. Evidence:

1. **License**: MIT, the most permissive (§3 vs gitnexus PolyForm-NC).
2. **Supply-chain**: SHA-pinned (strongest form per CR-9; §3 pin-form winner).
3. **Capability**: 13 unique-to-serena tools that gitnexus does not provide (§1 — find_symbol, replace_symbol_body, rename_symbol, find_referencing_symbols with code snippets, get_diagnostics_for_file, write_memory etc.).

5. **Bake-off**: failed Task A/B because the project was auto-activated as `rust`-only. This is **NOT a serena defect** — `.cargo/git/checkouts/` is a cargo cache dir; `.serena/project.yml` needs explicit `python` language config. 1-line fix.

### "Should we remove serena?"

**KEEP — with conditions**:

**Maintenance plan**:
1. **(P0, 5 min)**: edit `.serena/project.yml` and set `programming_languages: [python, rust, typescript]` (the actual workspace mix). Verify with `mcp__serena__get_symbols_overview harness/eval_harness.py` returning non-empty.
2. **(P1, ongoing)**: monitor for upstream serena commits — the SHA-pin `249f6b07…` is from before 2026-05-18; consider quarterly SHA bumps after diffing upstream commits for behaviour changes.
3. **(P2, optional)**: if serena's 21-tool surface bloats the tool-list-preload, evaluate disabling rarely-used tools (eg `delete_memory`, `rename_memory`) via `--enable-tools` flag at MCP launch.

**Rollback plan (if you decide to remove later)**:
- Delete the `"serena": {...}` block from `.mcp.json` (~4 lines).
- Restart CC (`/reload-mcp` or full restart).
- Smoke test: `which uvx && uvx --version` should still work; no uninstall needed (uvx is dependency-free).
- Recovery time: <60s.

### And gitnexus?

Separately recommend **KEEP gitnexus too** (T3 PATTERN-STUDY operationally; was already W259v15 STUDY-PILOT) **with these P0 maintenance items**:
