## §3 — Answer to the driving question

**Add a dedicated GraphRAG / vector-store MCP beyond the current stack?** **NO** — not today. Four reasons:

1. **No corpus (CR-1).** GraphRAG/vector-store MCPs need a real corpus. The runtime has only code (covered by gitnexus+serena+repomix) and episodic (memory+graphiti). cognee was pre-wired and the operator left :8000 closed — confirming the corpus-gap.
2. **No official MCP for any GraphRAG engine (CR-1).** LightRAG, microsoft/graphrag, nano-graphrag: zero official MCPs. Top community LightRAG bridge = 114★, no license — violates CR-1.
3. **`qdrant/mcp-server-qdrant` duplicates `memory`'s role.** It exposes `qdrant-store`+`qdrant-find` (DeepWiki-verified) — exactly what `doobidoo/mcp-memory-service` (3.72 MB live) already does. Per W262 §1, swapping costs the integration win.
4. **`context-mode` owns working-tier RAG** (FTS5 + auto-index via `ctx_batch_execute`); any added vector store would shadow it.

**Conditional STUDY**: `qdrant/mcp-server-qdrant` (adopt only if `memory` regresses or grows >50 MB); `topoteretes/cognee` MCP (re-add only when a doc-corpus workflow lands — `_comments.cognee_w259v8` recipe ready, reversibility HIGH).
