## §2 MIPROv2 — when to use vs BootstrapFewShot vs GEPA

**MIPROv2 = Multi-prompt Instruction Proposal Optimizer v2** (arXiv:2406.11695, Opsahl-Ong et al.).

Pipeline (per `dspy.ai/learn/optimization/optimizers/`):
1. **Bootstrapping stage** — run program many times, collect input/output traces per module, filter by metric.
2. **Grounded proposal stage** — preview program code + data + traces → draft many candidate instructions per prompt.
3. **Discrete search stage** — Bayesian Optimization over instruction × demo mini-batches.

**Pick MIPROv2 when**:
- You have a labeled `trainset` of ≥50 examples + a clear `metric` callable.
- Compute budget tolerates **medium rollout count** (default `auto="light"`/`"medium"`/`"heavy"` map to escalating eval budgets).
- Program is **multi-stage** (e.g., RAG retriever → reranker → generator) — MIPRO co-tunes instructions and demos across stages.
- You can tolerate ~hundreds of LM calls but not thousands.

**Pick BootstrapFewShot when**:
- Compute is tight (only need demos, not instructions).
- Single-module program.
- Small labeled set (8-20 examples).

**Pick GEPA when**:
- **Rollouts are expensive** (agent + tool calls + simulation): GEPA needs **100-500 evals vs 10K+ for RL** (gepa-ai/gepa README "When GEPA Shines").
- You can produce a **textual feedback signal** per example (error message, trace, reasoning critique) — not just a scalar.
- Working with **API-only models** (no weight access) — GEPA optimizes via reflection, not gradients.
- You need **interpretable optimization traces** (human-readable why-each-prompt-changed history).
- Data is **scarce** — GEPA works with as few as 3 examples.

**Anchor**: `https://dspy.ai/learn/optimization/optimizers/` §"Automatic Instruction Optimization"; `https://github.com/gepa-ai/gepa#when-gepa-shines`.

## §3 GEPA — Pareto-frontier reflective optimizer

**Paper**: arXiv:2507.19457 v2 (Feb 2026), "GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning", Agrawal/Tan/Soylu/...Stoica/Klein/Zaharia/Khattab et al. (16 co-authors). UC Berkeley + Stanford + MIT + Databricks org-co-stewardship.

**Core mechanism**:
1. **Sample trajectories** (reasoning + tool calls + tool outputs) from current prompts.
2. **Reflect in natural language** — LLM reads the FULL trace (error messages, profiling data, reasoning logs) and diagnoses _why_ the candidate failed.
3. **Propose targeted fixes** via reflection → new prompt candidates.
4. **Pareto-aware selection** — keep variants on the Pareto frontier of multi-objective scores, not single-best.
5. **Iterate** mutation + selection.

**Headline numbers**:
- **35× fewer rollouts than GRPO** (RL baseline, Group Relative Policy Optimization) on 4 LLMs (Llama-3.1-8B/70B + Mistral + Gemma) — W314-B Stream B benchmark synthesis.
- **Outperforms MIPROv2** on the same 4-LLM suite — paper §benchmarks (arXiv:2507.19457 abstract).
- **DSPy Full Program Adapter: 67% → 93% on MATH** — `gepa-ai/gepa` README adapter table.
- **+18% RAG/agent benchmarks** — cited in sca-v12.1 §Δ47 "evolving frontier dominates fixed-best by ≥18% on RAG/agent benchmarks".
- **100-500 evals vs 10K+ for RL** — `gepa-ai/gepa` README §"When GEPA Shines".
- **Works with 3 examples** — same source, "Scarce data" condition.

**Built-in adapters in `gepa-ai/gepa`** (canonical repo):
- `DefaultAdapter` — single-turn system-prompt optimization
- `ConfidenceAdapter` — logprob-aware classification (`pip install "gepa[confidence]"`)
- `DSPy Full Program` — evolves entire DSPy programs (signatures + modules + control flow)
- `Generic RAG` — vector-store-agnostic (ChromaDB / Weaviate / Qdrant / Pinecone)
- `MCP Adapter` — **optimizes MCP tool descriptions and system prompts** (direct relevance to this runtime's 22+ MCP servers)
- `TerminalBench` — Terminus terminal-agent
- `AnyMaths` — math reasoning

**Anchor**: `https://arxiv.org/abs/2507.19457`; `https://github.com/gepa-ai/gepa` README §"What is GEPA?" + §"Adapters" + §"When GEPA Shines".

## §4 GEPA+ (`sentient-agi/gepa-plus`) — multi-LLM proposer, NOT ROMA 4-role decomposition

**Brief correction**: The brief's framing — "Atomizer + Planner + Executors + Aggregator 4-role split; 2-6 point gains over GEPA with 3-4× fewer metric evals" — **does NOT match the actual sentient-agi/gepa-plus repo**. That repo is titled "**GEPA+: An Enhanced Prompt Proposer for GEPA**" and implements a multi-LLM proposal stage, not a 4-role decomposition. Treat the brief's ROMA framing as `[claim-not-substantiated by repo evidence]`.

**Actual `sentient-agi/gepa-plus` design** (per README §"Key Innovation"):

4-stage **PROPOSAL pipeline** (replaces GEPA's single-LLM proposer):
1. **Stage 1**: Parallel generation of K proposals from different LLM configurations (varied temperature + architecture)
2. **Stage 2**: LLM-as-a-judge evaluation (0-100 scoring)
3. **Stage 3**: Top-N selection
4. **Stage 4**: Intelligent merging to synthesize one final instruction

**Actual benchmark results** (README §"Benchmark Results", AIME mathematical reasoning, 150 test problems):

| Configuration | Test Accuracy | LLM Calls | Wall Time |
|---|---|---|---|
| Baseline (no optimization) | **50.0%** (75/150) | — | — |
| Standard GEPA (single GPT-4) | 42.7% (64/150) | 30 | 12 min |
| GEPA+ Faster (3× GPT-4 varied temp) | 40.0% (60/150) | 39 | 8 min |
| GEPA+ Faster (5 mixed models) | 44.0% (66/150) | 51 | 10 min |

**Critical observation**: On AIME, **baseline (no optimization) BEATS all GEPA variants by 6-10 points**. This suggests GEPA-on-AIME is the **wrong tool for that task class** rather than evidence of GEPA+ superiority. GEPA+ Faster also UNDERperforms Standard GEPA (40.0% vs 42.7%) in the 3× setting. The "2-6 point gains" claim in the brief appears to be **misattributed**.

Preliminary cross-task generalization claims (README §"Generalization"):
- HotPotQA: 5-8% improvement over baseline
- GSM8K: 3-5% improvement
- Classification: 2-4% improvement

These are **preliminary** (5 commits total in the repo) and not externally validated. Use with caution.
