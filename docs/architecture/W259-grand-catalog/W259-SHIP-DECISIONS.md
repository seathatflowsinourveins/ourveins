## §1 — Memory layer (L1.5) — PRIORITY deep-dive

**SHIP VERDICT: `vectorize-io/hindsight` (composite ~90) as the L1.5 memory engine — RECOMMENDED. `getzep/graphiti` (composite ~85) is INSTALLED-LIVE as the temporal/KG adjunct.**

The memory layer is the one place W259 *reversed itself*, and the reversal is the most important benchmark-integrity finding in the catalog. Wave-2 declared **mem0** the T1 PRIMARY citing "94.4% LongMemEval." W259-v4 caught the error: that 94.4% is **mem0's own SaaS-platform marketing number** (`mem0.ai/research`), and DeepWiki "verifying" it was simply echoing mem0's README. The OSS `Memory` class that an operator actually installs scores **49% LongMemEval under independent evaluation** (Vectorize.io 2026-03-14) — *last* among independently-evaluated engines — and a second independent rerun (`buildingjoshbetter/TrueMemory`) put it at 66%. mem0's own maintainers concede the gap (issues #2800/#3943: "the eval story for OSS isn't great"). mem0 markets **LoCoMo** (the easy ~9k-token benchmark) and conflates it with **LongMemEval** (the canonical hard 115k–1.5M-token ICLR-2025 benchmark). **mem0 → T3 DECLINED.**

The corrected winner is **Hindsight** — and the decisive fact is **integration completeness, NOT benchmark epistemics**. Hindsight's LongMemEval number is `[SELF-REPORTED]`, exactly like every other memory engine's: there is **NO independently-reproduced LongMemEval number anywhere in the memory field**, and **no official LongMemEval leaderboard exists** (the benchmark authors maintain none). *(CORRECTION — supersedes the prior W259-v4 claim: an earlier draft said Hindsight's score was "independently reproduced by Virginia Tech + The Washington Post." That is FALSE — arXiv 2512.12818 "Hindsight is 20/20" is **co-authored** by Virginia Tech (Srivastava/Wang/Ramakrishnan) and The Washington Post (Neeser) **alongside Vectorize.io**; those parties are on Hindsight's own byline. Co-authorship is vendor first-party work, not independent reproduction. The W259-v4 source — the Pith blog — misread the author list. See `03-deepdive/MEMORY-SOTA-EVIDENCE-AUDIT-W259v16.md` §Q2.)* Two contamination classes from the benchmark-integrity audit confirm benchmark rank cannot be the tiebreaker: (1) **LoCoMo has a documented 93.57% scoring ceiling** (99 gold-answer errors in 1,540 questions per `dial481/locomo-audit`) — any LoCoMo score above ~94% is mathematically suspect; (2) **LongMemEval leaderboards are judge-uncontrolled** — the Engram team measured a **52-point swing from LLM-judge choice alone** (same questions, same retrieval, same answerer). So the top three (OMEGA 95.4 / Mastra OM 94.87 / Hindsight 94.6) are a **statistical tie inside the judge-noise band** — and Hindsight wins the tie on the operationally-decisive axes: it is the **only memory engine with a full native-CC plugin** (hooks + MCP + skill), **MIT license**, *verified* Windows support (Docker/pip/embedded-pg0), zero cloud dependency, and **already installed in this runtime**. OMEGA's higher 95.4% is **unreproduced, single-author (~110★), Windows-untested, and self-admittedly not stress-tested past ~600 memories** — a long-arc `/loop` runtime exceeds that fast → OMEGA stays **OPERATOR-DECISION (pilot lane)**.

**The "hindsight-vs-mem0 correction" in one line**: the catalog's Wave-2 PRIMARY (mem0, 49% real) was replaced by Hindsight because Hindsight is the only memory engine with a complete native-CC plugin (hooks + MCP + skill), MIT-licensed and Windows-verified, whereas mem0's marketed 94.8% is an unreproducible vendor SaaS-marketing number whose installable OSS engine scores ~49-66% — the canonical W259 benchmark-integrity lesson. **Live status**: the operator's runtime currently runs `memory` (sqlite_vec retrieval) + `graphiti` (FalkorDB temporal-KG, Ollama-backed) — both INSTALLED-LIVE and verified. Graphiti satisfies the temporal-adjunct slot (Zep 71.2% — the best *non-self-promotional* number, agreed across 3 independent tables; the only catalog engine supporting FalkorDB). **Hindsight is the RECOMMENDED net-new install** — it closes the operator's exact stated gap ("Claude-Code-side hook+MCP integration") and per cardinal-rule-3 needs a codex Path P review before its `.mcp.json` + `settings.json` commit.

## §2 — RAG / retrieval layer (L0 substrate · L2.5 knowledge) — PRIORITY deep-dive

**SHIP VERDICT: there is no single "RAG framework" winner because W259 found RAG is correctly decomposed across layers — retrieval substrate, structured-knowledge extraction, and RAG-eval. The converged picks: `getzep/graphiti` GraphRAG (INSTALLED-LIVE) for retrieval + `pydantic-ai`/`instructor` (RECOMMENDED) for structured knowledge + `explodinggradients/ragas` (DECLINED — demand-gated) for RAG-eval.**

The benchmark-integrity audit is just as load-bearing here. The catalog's structured-output sub-layer (L2.5) is ranked on **BFCL (Berkeley Function-Calling Leaderboard, AST-verified)** + the `aastroza/structured-generation-benchmark` (the only independent benchmark that holds the model constant and measures the *library's* reliability uplift). That benchmark produced the layer's cleanest number: constrained decoding lifted `deepseek-coder-7b` from **38.9% → 87.0% BFCL AST** — which would crown **outlines**. But W259 caught a **use-class mismatch** (the same error-class as LoCoMo-vs-LongMemEval): outlines' constrained decoding **requires model-weight logit access and is unusable on Claude/GPT cloud APIs** — the operator's entire model surface. So **outlines → T3 DECLINED** (cite the "constrain-don't-validate" pattern; do not install), and the benchmark-correct *installable* winners are **`pydantic/pydantic-ai` (composite 88-89)** and **`567-labs/instructor` (composite 87-88)** — the only top candidates that work with cloud APIs. pydantic-ai edges instructor on native Pydantic Evals + multi-run pass^k. A second independent finding (**SOB**, arXiv 2604.25359) sharpens the warning: models hit ≥96% *schema compliance* but only **69-83% value accuracy** — "the scaffolding is correct, the content inside it is not." Schema-valid JSON is necessary, not sufficient — which is why a RAG-eval lane matters.

On the retrieval substrate itself, W259 confirms the operator's stated **trilayer** (热 OpenViking hot / 暖 Qdrant warm vector / 冷 Cognee+FalkorDB cold GraphRAG) — but with one hard correction: **cognee uses Kuzu by default and does NOT support FalkorDB** (DeepWiki-verified, correcting the operator catalog). FalkorDB belongs with **Graphiti**, which is exactly how the live runtime is wired (`graphiti` MCP → FalkorDB :16379). For the cold GraphRAG tier, the installable bridge is **`cognee-mcp`** (Apache-2.0, inside the cognee monorepo) over **HTTP transport** — the operator-quickstart `uvx cognee-mcp` stdio form **hangs the MCP handshake on Windows** (CC respawn-loop, 75 orphan processes observed). The `.mcp.json` already carries a correct `type:http` cognee entry, INERT until the operator starts the supervised server → **OPERATOR-DECISION**. RAG-eval (**ragas**, composite 82-83) is **DECLINED / demand-gated** — no value until a standalone RAG sub-system is load-bearing; the eval harness already covers the eval need via Inspect AI + promptfoo.
