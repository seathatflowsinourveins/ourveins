## Root cause (definitive)

1. **Mechanism** (Phase 0 Stream A, `pre-commit/pre-commit @f35134b` v4.6.0): pre-commit's "files were modified by this hook" check (`commands/run.py:206`) is byte-equality of `git diff` stdout — baseline taken after its custom patch-stash (`run.py:294`), post-hook taken right after the hook returns (`run.py:203`). The diff covers the ENTIRE working-tree-vs-index for ALL tracked files (no `files:` regex filter). The check runs after EVERY hook, framework-level and hook-agnostic.
2. **The hook is innocent** (Phase 0 Stream C): `tools/precommit-msys-hooks-form.mjs` makes 4 read-only fs calls (`readdirSync`/`statSync`/`readFileSync`/`existsSync`), zero write APIs. It cannot be the writer.
3. **Not CRLF** (Phase 0 Stream B + Phase 2 bisect): this repo is `core.autocrlf=input` + `.gitattributes eol=lf` + currently-aligned `i/lf w/lf`; the failure is autocrlf-INVARIANT (reproduces identically under input/true/false), falsifying every CRLF-round-trip explanation (P1 autocrlf-retry, P2 .gitattributes-in-stash) and the P3 version-regression theory.
4. **The writer is external + concurrent** (Phase 2 ISOLATED-REPRO): single-session control never reproduces (16/16 PASS); a controlled concurrent tracked-file writer reproduces every time (11/11 FAIL). The leading concrete mechanism — a concurrent CC session sharing the worktree — was corroborated LIVE: during the Phase 2 experiment a second session staged `.claude/skills/*.md` into this very worktree, and the SHIP INCIDENT (`7f3b733`) earlier in this wave was the same pathology.

## Fix (Case B)

**B-1 (structural) — worktree isolation. STATUS: SHIPPED (W363).** One git worktree per concurrent CC session ⇒ no shared-worktree tracked-file writes ⇒ no cross-session hook-window collision. Mechanized by:
- `tools/eee.ps1 --Wave Wn --Slug s` — wave-launcher that creates/uses a per-wave worktree (commit `7bf1e73`).
- `tools/preagent-wave-lock-guard.mjs` + `wave-lock validate` pre-commit hook — enforcement layer that validates wave-lock to prevent same-branch worktree collision (W363).
Phase 2's control experiment is the proof: with no second writer in the worktree, msys-hooks-form passes consistently (16/16). Per CLAUDE.md parallel-session-safety (W280d + W342-Z): "one git worktree per session", ~5 parallel cap.

**B-2 (operator mitigation for forced shared-worktree) — `git stash --keep-index` isolation. STATUS: PROVEN this wave.** When a worktree MUST be shared, stashing unstaged tracked WIP before commit + popping after narrows the race window. Used 6× successfully this wave (commits `b29b10a`, `56966d1`, `cfc00a3`, `1b28abe`, `b996c09` + the SHIP INCIDENT recovery). NOTE: this reduces but does not eliminate the race — a concurrent writer landing inside the commit's own hook window can still trip the gate; it is a transition-period mitigation, not a substitute for B-1.

**B-3 (upstream) — pre-commit issue. STATUS: DEFERRED (non-blocking).** File a `pre-commit/pre-commit` issue documenting the concurrent-writer pathology of `staged_files_only.py`'s patch-stash + full-tree byte-diff detection on shared worktrees. Out of scope for this wave.

**No code change to the hook or config.** Per CR-6 + YAGNI: the framework behavior is correct-by-design and the structural fix is operational + already shipped. Writing speculative in-hook mitigation code that cannot fully close a timing race would add complexity without resolving the root cause. The investigation's deliverables are the diagnostic tool (Phase 1, reusable for sibling gates) + the confirmed evidence chain + this resolution record.
