### How to apply

1. **Classify task risk-class FIRST** (BEFORE writing T1 consult or scoping the ship):
   - Examine target file class (cardinal-rule surface? rule-layer? script? test?)
   - Examine LOC delta (≤200 LOC bounded vs >200 LOC architectural)
   - Examine reversibility (pure additive doc-only? behavioral mechanism change? security/destructive?)
   - Examine cite-class novelty (new TIER-1/TIER-2 source class introduced? new cite anchor pattern?)
2. **Select gate-set per risk-class** (per §The 3-tier risk taxonomy table above)
3. **Document risk-class in commit body** — include `risk-class: low | medium | high` line + 1-line classification rationale (e.g., `risk-class: medium — multi-file rule edit + new mechanics introduced; T1+T2+T3 lifecycle invoked`)
4. **Risk-class is REVISABLE pre-commit** — if T1 surfaces unanticipated cardinal-surface impact (e.g., the rule edit changes existing T-touchpoint semantics rather than adding a new section), upgrade to high-risk and fire T0+T5 retroactively before commit

### Anti-patterns

- **"All changes go through medium-risk gate"** — refuted by Anthropic taxonomy (Wave-6 Agent M source). Low-risk operations (test files, doc-only updates, additive bounded sections with no behavior change) are over-gated by medium-risk T1+T2 coverage; the medium-risk full lifecycle costs ~5-10 min per ship unnecessarily. Conversely, high-risk operations (CLAUDE.md cardinal-rule trim, settings.json env block changes, .mcp.json server addition) are under-gated by medium-risk-only T1+T2 — they need T0 candidate-list challenge + T5 plan-stage review BEFORE T1 fires.
- **Risk-class as severity proxy** — they're orthogonal axes. A low-risk ship can produce a P0 finding (e.g., test file accidentally exposes secret). A high-risk ship can produce only P3 findings (e.g., CLAUDE.md trim with all changes anticipated by design review). Don't conflate.
- **Static risk-class declaration without re-classification trigger** — if T1/T2 surfaces unanticipated cardinal-surface ripple, the original low-risk classification is invalid; re-classify to medium or high per the surface impacted, do NOT silently proceed under the original risk-class.

## Why this rule exists

The prior default was "wait for n≥2 before codifying" (parent cycle-273 close report), which protected against over-specification from small samples. But three consecutive n=1 codifications (parent cycle-296, 318, 319) have all held against subsequent applications without revision — the n≥2 bar was a proxy for "avoid premature codification" when the root metric is **cost-per-miss**.

Codifying too early costs LOC in a reference file (~50-150 LOC typical). Codifying too late costs re-derive time at each future application. For patterns where re-derive is cheap (~minutes), waiting for n=2 is effectively free. For patterns where re-derive is expensive (>15 min), every "wait for n=2" burns 15+ min on the next application — and if frequency is several per month, the wait dominates.
