## How to apply

1. **Detect drift** — read `.claude/state/sota_pin_audit.jsonl` last row OR run the `sota_freshness_sweep` audit interactively after the repo-local script lands. 3. **Surgical edit** — single-axis bump: edit ONE `PINS.json` entry (or ONE `tools-pin.txt` line). Update `verified: YYYY-MM-DD`. Commit with `chore(pins): bump <category>.<key> <old>→<new>` prefix for greppable `git log`.

5. **Atomic batch is OPTIONAL here** — unlike `.claude/rules/audit-action-loop.md` count-claim drift (which needs atomic-batch with the ship that introduced the count change), SOTA-pin bumps are typically standalone events. Bundle only if multiple categories drifted simultaneously from the same root cause (e.g. weekly external update wave).

## Why

SOTA references decay faster than code references. A function rename triggers a search-and-replace; a model-SHA rebake or a `pyrefly 0.61.1 → 0.62.0` upstream bump produces zero local symptoms — until someone runs the audit. Unwired audits miss this entirely; wired-but-unactioned audits accumulate noise and stop being trusted. The 4-stage discipline (Wire → Surface → Close → Re-fire) is what converts "we have an audit" into "the SOTA stack is current."

The SessionStart consumer is WARN-only by design — drift signals belong in the cold-start brief, not in inline blocking.

## When NOT to apply

- **Single-fire saturation** — if 4+ categories drifted, picking ALL violates ONE-LOGICAL-UNIT-PER-FIRE. Pick the one with the strongest blast radius (model SHAs > codex CLI > MCP inventory > others) and defer the rest.
- **Audit script itself broken** — if JSONL records contain `PROBE_ERROR: cmd_not_found` rows, fix the env or skip the probe BEFORE chasing pin drift.
- **Network-probe scope creep** — Tier-2 (star counts) and Tier-3 (citation-anchor content equality) intentionally use NO network. Don't add `gh api` calls into the SessionStart hot path; queue for separate audit script.
- **Cross-session race** — if a parallel session is mid-bump, prefer `git stash` + commit + restore rather than racing the same `PINS.json` line.

## Anti-patterns

- **Stop-and-handoff at threshold as a mandatory halt** — refuted by GSD advisory pattern (`gsd-context-monitor.js:158-159` "never use imperative commands that override user preferences") + wshobson `/context-save` + `/context-restore` persist/restore command pattern. The advisory threshold is an automation trigger for the save→compact→restore loop, NOT a hard limit. This does NOT refute "wrap up the current logical unit" — GSD's own warning text still advises avoiding new complex work at low remaining context. The recalibration distinguishes "finish / compact / continue" (Rank #3 loop) from "commit + `/clear` hard stop" (wrong).
- **Hook `decision:block` for compaction** — refuted by Rank #3 scope discipline + Rank #3.5 CRITICAL note. Rank #3 is operational agent discipline triggered by advisory signals; Rank #3.5 PreCompact/PostToolUse/SessionStart hooks MUST continue exit-0 / no `decision:block`. The Rank #3 recalibration is NOT permission to convert advisory hooks into a gate.
- **Let autocompact fire blind at the local target/default boundary** — refuted by `karpathy-adapted.md §5` + Thariq tip 2026-04-16. Autocompact at the model's "least intelligent point" produces lossy summaries with no operator steering. The Rank #3 pre-emptive save→compact→restore loop is the SOTA.
- **Read large files into context for analysis** — refuted by file_writing_policy + ctx_execute discipline. Use `ctx_execute_file(path, code)` to process in sandbox; only printed answer enters context.
- **Bash for >20-line commands** — refuted by PreToolUse hook guidance. Route through `ctx_execute(language: shell)` or `ctx_batch_execute`.
- **Multiple ctx_execute calls when one batch suffices** — refuted by ctx_batch_execute description. One call replaces 30+ ctx_execute + 10+ ctx_search calls.
- **Repeated Read of same large file** — refuted by progressive disclosure. Read once, persist findings to a topic-scoped memory file, reference from there.
- **MEMORY.md content-as-entries** (writing content directly into the index) — refuted by Karpathy §5 Layer-2 vs Layer-3 distinction. Index = pointers; content = linked files.
- **Subagent for sub-1000-token operations** — refuted by `parallel-agent-wave.md §Fork-vs-fresh`. Subagent overhead > savings for trivial ops.

#### Ancestor Loading (UP the directory tree)

When you start Claude Code, it walks **upward** from your current working directory toward the filesystem root and loads every CLAUDE.md it finds along the way. These files are loaded **immediately at startup**.

#### Descendant Loading (DOWN the directory tree)

CLAUDE.md files in subdirectories below your current working directory are **NOT loaded at launch**. They are only included when Claude reads files in those subdirectories during your session. This is known as **lazy loading**.

### Example Monorepo Structure

Consider a typical monorepo with separate directories for different components:

```
/mymonorepo/
├── CLAUDE.md          # Root-level instructions (shared across all components)
├── frontend/
│   └── CLAUDE.md      # Frontend-specific instructions
├── backend/
│   └── CLAUDE.md      # Backend-specific instructions
└── api/
    └── CLAUDE.md      # API-specific instructions
```

### Scenario 1: Running Claude Code from the Root Directory

When you run Claude Code from `/mymonorepo/`:

```bash
cd /mymonorepo
claude
```

| File | Loaded at Launch? | Reason |
|------|-------------------|--------|
| `/mymonorepo/CLAUDE.md` | Yes | It's your current working directory |
| `/mymonorepo/frontend/CLAUDE.md` | No | Loaded only when you read/edit files in `frontend/` |
| `/mymonorepo/backend/CLAUDE.md` | No | Loaded only when you read/edit files in `backend/` |
| `/mymonorepo/api/CLAUDE.md` | No | Loaded only when you read/edit files in `api/` |

### Scenario 2: Running Claude Code from a Component Directory

When you run Claude Code from `/mymonorepo/frontend/`:

```bash
cd /mymonorepo/frontend
claude
```

| File | Loaded at Launch? | Reason |
|------|-------------------|--------|
| `/mymonorepo/CLAUDE.md` | Yes | It's an ancestor directory |
| `/mymonorepo/frontend/CLAUDE.md` | Yes | It's your current working directory |
| `/mymonorepo/backend/CLAUDE.md` | No | Different branch of the directory tree |
| `/mymonorepo/api/CLAUDE.md` | No | Different branch of the directory tree |

### Key Takeaways

1. **Ancestors always load at startup** — Claude walks UP the directory tree and loads all CLAUDE.md files it finds. This ensures you always have access to root-level, repository-wide instructions.

2. **Descendants load lazily** — Subdirectory CLAUDE.md files only load when you interact with files in those subdirectories. This prevents irrelevant context from bloating your session.

3. **Siblings never load** — If you're working in `frontend/`, you won't get `backend/CLAUDE.md` or `api/CLAUDE.md` loaded into context.

4. **Global CLAUDE.md** — You can also place a CLAUDE.md at `~/.claude/CLAUDE.md` in your home folder, which applies to ALL Claude Code sessions regardless of project.

### Why This Design Works for Monorepos

- **Shared instructions propagate down** — Root-level CLAUDE.md contains repository-wide conventions, coding standards, and common patterns that apply everywhere.

- **Component-specific instructions stay isolated** — Frontend developers don't need backend-specific instructions cluttering their context, and vice versa.

- **Context is optimized** — By lazily loading descendant CLAUDE.md files, Claude Code avoids loading potentially hundreds of kilobytes of irrelevant instructions at startup.
