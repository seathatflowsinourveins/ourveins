## The rule

Every launch should be **reversible, observable, and incremental**. The goal is not just to deploy — it's to deploy safely with monitoring in place, a rollback plan ready, and a clear definition of success.

## When this discipline applies

ANY of these triggers fires this rule:

1. Deploying a feature to production for the first time

## The 3 launch invariants

### 1. Reversible

Every launch ships WITH a tested rollback path. Two-button rollback minimum:
- **Code rollback**: `git revert` + redeploy succeeds
- **Data rollback**: backup-restore path exercised at least once before launch
- **Config rollback**: feature flags / settings reverted via single edit
- **External effects**: side-channel rollback (cancel emails, refund charges, undo analytics events)

If any of these is irreversible, classify as **HIGH-RISK** + require explicit operator override + extended monitoring window.

### 2. Observable

Before traffic flips, monitoring + alerting are in place AND tested:
- **Logs**: aggregating to known sink with retention
- **Metrics**: error rate / latency / saturation tracked with baseline
- **Traces**: distributed tracing on critical paths
- **User-facing signals**: 5xx error rate, 4xx anomaly, success-criteria event counter
- **Alert validation**: trigger a test alert; verify oncall receives it

### 3. Incremental (staged rollout)

Avoid all-or-nothing flips:

| Stage | % Traffic | Duration | Gate |
|---|---|---|---|
| Internal | 0-1% (employees only) | 1-2 days | Zero P0 incidents |
| Beta | 5-10% | 1 week | Error rate < baseline; success metrics ≥ threshold |
| Half | 50% | 3-7 days | Both pop'ns observable + comparable |
| Full | 100% | — | Beta + Half stages clean |

Rollback at ANY stage if invariants 1+2 fire.

## Post-launch monitoring window

For 24-72h post-launch:
1. Daily review of metrics + logs
2. Compare error rate vs baseline (delta should be ≤ 5%)
3. User feedback channels monitored
4. On-call rotation aware of launch
5. Any rollback decision per `cross-model-consensus.md` Outcome A/B/C disposition (cite-import-AMBER):

   - **Outcome B** (regression observed) → REVERT + post-mortem
   - **Outcome C** (partial regression with mitigation) → manual override + extended observation

When `CLAUDE_CODE_SUBAGENT_MODEL` is set to a model OTHER than the canonical gpt5-reviewer / gpt5-archaeologist target (currently `gpt-5.5` via codex CLI), the subagent runs as a **same-model stand-in** rather than a true cross-model voice. The cross-model consensus invariant — that codex GPT-5.5 catches what Opus/Sonnet self-audit miss — does NOT structurally hold under stand-in dispatch. The dispatch surface looks identical to the orchestrator (same agent name, same prompt template, same return shape) but the model-asymmetry that makes the gate meaningful is silently absent.

### The mandate

A `gpt5-reviewer` / `gpt5-archaeologist` dispatch under env-funneling MUST do ONE of:

1. **(Default)** Return `VERDICT: BLOCK` per the agent's fail-closed contract at `.claude/agents/gpt5-reviewer.md` frontmatter. Stand-in dispatch does NOT satisfy the cross-model gate; BLOCK is the safe action under structural same-model degradation.
2. **(Explicit-disclosure)** Return APPROVE / NEEDS-REVISION / REJECT WITH explicit `STAND-IN-NOTICE: agent ran under CLAUDE_CODE_SUBAGENT_MODEL=<model> stand-in per CLAUDE.local.md ENV block (f); cross-model gate NOT structurally satisfied for this dispatch` in the verdict body's first 5 lines. The orchestrator then bears the integration decision: re-fire via real codex CLI, accept stand-in verdict with documented gate-bypass rationale, or REVERT-AND-REMOVE per `closed-loop-recursive-narrowing.md` Outcome B.
3. **(Operator escalation)** If codex CLI is unreachable (FM-03 D1 transport): return BLOCK + queue-and-retry per the existing "On codex unavailable" recovery options at §"Timeout + failover policy" above.

### Orchestrator integration discipline

When integrating a STAND-IN-NOTICE verdict into a composite synthesis (e.g., Wave fan-out close-synthesis.md), the orchestrator MUST:

1. **Surface the stand-in penetration rate** in the close-synthesis verdict body — e.g., "5/9 dispatches ran as Sonnet stand-in (~56%); cross-model coverage is ~44% of nominal; treat composite verdict accordingly".
2. **Reject blanket "N% GPT-5.5 dispatched" claims** without per-dispatch classification (true GPT-5.5 via `codex exec` CLI vs Sonnet stand-in via Anthropic SDK vs codex-rescue wrapper-around-codex-CLI). 3. **Cite the stand-in classification** in commit body when the ship integrates a stand-in verdict (e.g., `T1 NEEDS-REVISION conf=0.83 [STAND-IN per CLAUDE.local.md ENV (f); see tmp/wave17-E2-arc-level-review-2026-05-04.md §5]`). ## Rule: Every new pattern MUST cite its source at file:line depth

1. **Header comment**: `# Reference: Z:/repos/deps/<repo>/<file>:<line>` or `# Reference: <official-docs-URL>`
2. **Never cite READMEs alone** — cite the actual source code implementation
3. **Star count does NOT indicate quality** — read the source, verify the claim
4. **Verify before trust** — the cited file must still exist AND still say what you cite (labels decay)
5. **Silent fallback = violation** — if expected output doesn't appear (e.g., `embeddings: 0` after `--embeddings`), that's a STOP, not a footnote (parent `feedback_reference_first_hard_rule.md` — PARENT-ATTRIBUTION pending sss memory port)
6. **TIER-1-NAMED-AUTHOR-QUOTE class for inherited patterns** — when a SOTA pattern is derived from a named author's published work (book / peer-reviewed paper / conference talk), cite verbatim-quote + author-name + publication inline. The named-author cite is TIER-1 primary-source for the PATTERN (not the implementing repo); use alongside repo file:line cites for full provenance. Exemplar: `Z:/repos/deps/mattpocock/skills/README.md` (48,857★, MIT, [VERIFIED 2026-04-30 PM via curl raw GitHub]) quotes Pragmatic Programmer (Thomas & Hunt) for "rate of feedback is your speed limit" (failure-mode #3 framing), Domain-Driven-Design (Eric Evans) for ubiquitous-language pattern (#2 framing), and Extreme Programming Explained (Kent Beck) for "invest in design every day" (#4 framing). Per `.claude/projects/Z--claude-sota-installed/memory/reference_mattpocock_skills_pattern_extract_2026_04_30.md` for the full mining trace + adoption-candidate ranking. **TIER-1-NAMED-AUTHOR-QUOTE PROVISIONAL-EXCEPTION** *(round-3 framing per T3 round-2 conf=0.88 ESCALATING finding on commit `d4df352`; supersedes round-1 "full cardinal-rule-1 satisfaction" framing — physical-only sources do NOT fully satisfy committed-tree inspectability)*: physical-only printed-book/journal/conference-publication primary anchor (ISBN + page + verbatim-quote) is a PROVISIONAL-EXCEPTION to cardinal-rule-1 (CLAUDE.md L7), NOT full satisfaction. Cite class downgraded to TIER-1-NAMED-AUTHOR-QUOTE-PROVISIONAL with REQUIRED metadata: (a) ISBN/DOI + page + verbatim-quote inline; (b) verifier-identity disclosure (who-verified-when, e.g., `[VERIFIED 2026-05-04 by orchestrator against book Tip #15 verbatim text]`); (c) explicit `non-automatable: true` marker so review hooks know to defer to human sign-off; (d) **HARD-GATE ELIGIBILITY TEST** *(Round-3 amendment a per T3 R3 NEEDS-ATTENTION conf=0.82 same-class finding on commit `1b87a6e`; supersedes round-2 "MUST prefer" soft preference framing — preference is not gateable; eligibility is)*: PROVISIONAL admission is admissible ONLY when DOI landing page + accessible PDF / publisher excerpt / archived scan (license-permitting) was SEARCHED AND UNAVAILABLE. The commit body MUST document the search (which DOI/publisher/archive was queried + return shape — e.g., "searched ACM DOI 10.1145/<doi> 2026-05-05 — paywall-only, no excerpt found; searched Internet Archive — no scan; searched publisher excerpt page — none"). Mere preference is INSUFFICIENT — if any auditable surrogate exists (DOI/PDF/excerpt/scan), use it as the normative source instead of the physical-only book cite. e.g., ACM DOI `https://dl.acm.org/doi/10.1145/<doi>` for ACM papers IS auditable when paywall-free. Secondary aggregator URLs (Wikipedia, `https://pragprog.com/tips/`, `https://martinfowler.com/bliki/<topic>.html`, `c2.com/cgi/wiki`) are VERIFICATION PROXIES only — they help re-verify the primary quote without owning the book physically, but are NOT cited as normative source. **Independent named-reviewer sign-off mandate** *(Round-3 amendment b per T3 R3 NEEDS-ATTENTION conf=0.82 same-class finding on commit `1b87a6e`; supersedes round-2 "Lower-confidence reviewer-sign-off mandate" sole-orchestrator framing — sole-orchestrator verification is no longer admissible)*: rule edits citing TIER-1-NAMED-AUTHOR-QUOTE-PROVISIONAL MUST cite a SECOND verifier-identity BEYOND the orchestrator who replayed the verbatim quote against the source — commit body MUST embed BOTH verifier-identity-1 (the orchestrator, e.g., `[VERIFIED 2026-05-05 by orchestrator against book Tip #15 verbatim text]`) AND verifier-identity-2 (the independent named reviewer, e.g., `[VERIFIED 2026-05-05 by <human-name> against same book + same page + same quote]`) with explicit `[VERIFIED yyyy-mm-dd by <name> against <source>]` markers for each. 8. **Composed-claims discipline + mechanical source-class reduction lattice** — *(Wave 17 fire-31 v1 codification per codex T1 fire-28 conf=0.87; UPGRADED at fire-36 per codex T1 fire-33 NEEDS-REVISION on T2 b8fa7dd1 finding "weakest-source rule not computable" conf=0.72)* — When a single normative claim cites MULTIPLE source classes, the cite MUST declare:
   - `constituents=[<class1@cite1>, <class2@cite2>, ...]` — explicit list of each constituent primitive at file:line + SHA OR official-docs URL
   - `effective_tier=<class>` — the EFFECTIVE class of the composed claim, computed by the reduction lattice below

   **Source-class precedence/order (lower wins; weakest dominates)**:
   1. `UNKNOWN` (no cite at all) — always disqualifying; reject claim until cited
   2. `TIER-3-LOCAL-COMPOSITION` (any local glue / sss-novel composition over TIER-1/TIER-2 substrates)
   3. `TIER-3-LOCAL-OPERATOR-DERIVED` (sss dogfood, codex verdicts, incidents, operator decisions)
   4. `TIER-3-LOCAL-CONFIG` (sss live config or script wiring)
   5. `TIER-2` (user-curated/sibling docs, NOT upstream authority)
   6. `TIER-1-COMPOSED` (ALL constituents TIER-1 with disclosed local glue) — still TIER-3-LOCAL-COMPOSITION as effective tier
   7. `TIER-1-DIRECT` (upstream verbatim file:line + SHA OR official-docs URL with anchor)

   **Reduction rule (mechanical)**: `effective_tier = MIN_PRECEDENCE(constituents)`. Concretely: if ANY constituent contains "TIER-3-LOCAL-*" OR the composition glue itself is local-codified (e.g., sss-novel composition pattern), the effective tier is `TIER-3-LOCAL-COMPOSITION` regardless of how many TIER-1 primitives are cited. EXCEPTION: if the composed claim is ONLY about an upstream primitive's EXISTENCE (e.g., "asyncRewake field exists" cited verbatim from Anthropic docs), it remains `TIER-1-DIRECT` because there's no local composition glue.

   **Anti-promotion rule**: composition CANNOT promote a TIER-2/TIER-3 component into TIER-1. The cite class of the COMPOSED claim is determined by the MIN_PRECEDENCE constituent OR by the composition-glue class, whichever is weaker.

   **Exemplar (computable)**: `.claude/rules/cross-model-consensus.md §Normative Authority Map` row "T1-T7 touchpoint lifecycle":
   - `constituents=[TIER-1-DIRECT @ Anthropic-CC-hooks-docs-L1021-1023, TIER-2 @ CCBP-cross-model-workflow.md:1-48, TIER-3-LOCAL-COMPOSITION @ sss-novel T0+T7+profile-selection]`
   - `effective_tier=TIER-3-LOCAL-COMPOSITION` (MIN_PRECEDENCE = 2 due to sss-novel glue)
   - Despite Anthropic CC + CCBP being upstream-authority for primitives, the composition itself is eee-local and EFFECTIVE class is TIER-3-LOCAL-COMPOSITION

   Apply to: any rule body section in `.claude/rules/**` that mixes upstream + sister-rule + local-operator-codification claims. Sister: `cross-model-consensus.md §Normative Authority Map` (POINTS TO this rule, does NOT carry softer duplicate).

  14: ## The rule
  15: 
  16: Every launch should be **reversible, observable, and incremental**. The goal is not just to deploy — it's to deploy safely with monitoring in place, a rollback plan ready, and a clear definition of success.
  17: 
  18: ## When this discipline applies
  19: 
  20: ANY of these triggers fires this rule:
  21: 
  22: 1. Deploying a feature to production for the first time
  23: 2. Releasing a significant change to users
  24: 3. Migrating data or infrastructure
  25: 4. Opening a beta or early-access program
  26: 5. Wiring a new MCP server, hook, plugin, or rule into runtime path
  27: 6. Modifying load-bearing config (`settings.json` permissions / hooks / `.mcp.json` / cardinal rules)
  28: 7. Any deployment that carries risk (all of them per Osmani)
  29: 
  30: ## Pre-launch checklist (6-axis)
  31: 
  32: ### Code quality
  33: - [ ] All tests pass (unit + integration + e2e)
  34: - [ ] Build succeeds with no warnings
  35: - [ ] Lint + type checking pass
  36: - [ ] Code reviewed + approved (cross-model T1+T2+T3 per `cross-model-consensus.md` if design-surface)
  37: - [ ] No TODO comments that should resolve before launch
  38: - [ ] No debugging artifacts (`console.log`, `print()`, scratch files)
  39: - [ ] Error handling covers expected failure modes
  40: 
  41: ### Security
  42: - [ ] No secrets in code or version control (cardinal-rule "NEVER commit secrets")
  43: - [ ] Vulnerability scan clean (`npm audit`, `pip-audit`, `cargo-audit`, `trivy fs`)
  44: - [ ] Input validation on user-facing endpoints
  45: - [ ] Authentication + authorization checks
  46: - [ ] Security headers configured (CSP / HSTS / etc) where applicable
  47: - [ ] Rate limiting on auth endpoints
  48: - [ ] CORS configured to specific origins (not wildcard)
  49: 
  50: ### Performance
  51: - [ ] Core Web Vitals within "Good" thresholds (frontend)
  52: - [ ] No N+1 queries in critical paths (backend)
  53: - [ ] Bundle size within budget
  54: - [ ] Caching configured for static assets + repeated queries
  55: - [ ] Database indexes verified for query patterns
  56: 
  57: ### Accessibility (frontend launches)
  58: - [ ] Keyboard navigation works for interactive elements
  59: - [ ] Screen reader can convey page structure
  60: - [ ] Color contrast WCAG 2.1 AA (4.5:1 for text)
  61: - [ ] No accessibility warnings in axe-core / Lighthouse
  62: 
  63: ### Infrastructure
  64: - [ ] Health check endpoint responds
  65: - [ ] Monitoring + alerting configured BEFORE launch
  66: - [ ] Logs aggregating to known sink
  67: - [ ] Rollback strategy documented + tested
  68: - [ ] Database backups verified (point-in-time recovery if data-touching)
  69: 
  70: ### Communication
  71: - [ ] Launch announcement drafted (internal + external)
  72: - [ ] Support team briefed
  73: - [ ] Documentation updated (runbook + user-facing)
  74: - [ ] Success criteria defined + measurable
  75: 
  76: ## The 3 launch invariants
  77: 
  78: ### 1. Reversible
  79: 
  80: Every launch ships WITH a tested rollback path. Two-button rollback minimum:
  81: - **Code rollback**: `git revert` + redeploy succeeds
  82: - **Data rollback**: backup-restore path exercised at least once before launch
  83: - **Config rollback**: feature flags / settings reverted via single edit
  84: - **External effects**: side-channel rollback (cancel emails, refund charges, undo analytics events)
  85: 
  86: If any of these is irreversible, classify as **HIGH-RISK** + require explicit operator override + extended monitoring window.
  87: 
  88: ### 2. Observable
  89: 
  90: Before traffic flips, monitoring + alerting are in place AND tested:
  91: - **Logs**: aggregating to known sink with retention
  92: - **Metrics**: error rate / latency / saturation tracked with baseline
  93: - **Traces**: distributed tracing on critical paths
  94: - **User-facing signals**: 5xx error rate, 4xx anomaly, success-criteria event counter
  95: - **Alert validation**: trigger a test alert; verify oncall receives it
  96: 
  97: ### 3. Incremental (staged rollout)
  98: 
  99: Avoid all-or-nothing flips:
 100: 
 101: | Stage | % Traffic | Duration | Gate |
 102: |---|---|---|---|
 103: | Internal | 0-1% (employees only) | 1-2 days | Zero P0 incidents |
 104: | Beta | 5-10% | 1 week | Error rate < baseline; success metrics ≥ threshold |
 105: | Half | 50% | 3-7 days | Both pop'ns observable + comparable |
 106: | Full | 100% | — | Beta + Half stages clean |
 107: 
 108: Rollback at ANY stage if invariants 1+2 fire.
 109: 
 110: ## Post-launch monitoring window
 111: 
 112: For 24-72h post-launch:
 113: 1. Daily review of metrics + logs
 114: 2. Compare error rate vs baseline (delta should be ≤ 5%)
 115: 3. User feedback channels monitored
 116: 4. On-call rotation aware of launch
 117: 5. Any rollback decision per `cross-model-consensus.md` Outcome A/B/C disposition (cite-import-AMBER):
 118:    - **Outcome A** (clean APPROVE post-monitoring) → ratify + close
 119:    - **Outcome B** (regression observed) → REVERT + post-mortem
 120:    - **Outcome C** (partial regression with mitigation) → manual override + extended observation

 138: ## Anti-patterns
 139: 
 140: - **Ship-and-pray**: deploying without monitoring in place. Refuted by §Observable invariant 2.
 141: - **Big-bang launch**: 0% → 100% traffic flip without staging. Refuted by §Incremental invariant 3.
 142: - **Irreversible launch with no override audit**: shipping a one-way door without explicit HIGH-RISK classification. Refuted by §Reversible invariant 1.
 143: - **Skip-monitoring-window**: declaring launch "done" at deploy-time without 24-72h observation. Refuted by §Post-launch monitoring window.
 144: - **Confuse T5 plan-review with T6 pre-launch**: plan-time and deploy-time are distinct gates. Plan-review checks design soundness; pre-launch checks deployment readiness. Run both, not one.

   6: # Shipping and Launch
   7: 
   8: ## Overview
   9: 
  10: Ship with confidence. The goal is not just to deploy — it's to deploy safely, with monitoring in place, a rollback plan ready, and a clear understanding of what success looks like. Every launch should be reversible, observable, and incremental.
  11: 
  12: ## When to Use
  13: 
  14: - Deploying a feature to production for the first time
  15: - Releasing a significant change to users
  16: - Migrating data or infrastructure
