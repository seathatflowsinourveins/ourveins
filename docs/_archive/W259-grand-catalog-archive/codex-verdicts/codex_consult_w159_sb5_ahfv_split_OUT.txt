## The rule

Sota-researcher / architect / general agent dispatches that surface SOTA candidates MUST include a **harness-fit verification step** asking "is this applicable to OUR specific architecture?" — beyond the convergence-gate Axis 1+2+3 (T1 sources / T2 practitioners / Axis 3 stability) that scores SOTA-status. Without harness-fit, candidates pass convergence-gate AND still fail at ship-target verification because of architectural mismatch invisible to upstream-source-only audit.

This is **convergence-gate Axis 4** (harness-fit) — separate from Axis 1+2+3 (which classify SOTA-status of the candidate ITSELF) and applied AFTER convergence-gate PASS, BEFORE ship-target verification.

## When this rule applies

Whenever an agent (sota-researcher / architect / general-purpose / Explore / code-reviewer / debugger) returns a ship-candidate ranking from a Wave-N dispatch:

1. The agent's convergence-gate verdict is necessary BUT NOT SUFFICIENT for ship-readiness
2. The candidate may be valid SOTA AND inapplicable to claude-sota
3. Apply the 4-axis harness-fit probe BEFORE writing T1 consult prompt OR queuing the ship

## How to apply (4-axis probe)

Before declaring an agent's ship-candidate "ready":

### Probe 1 — count-OVER

If the candidate claims a count delta (commit count, file count, line count, star count): verify against authoritative local source (`git log`, `wc -l`, `Glob | wc -l`, `mcp__github__search_repositories` star refresh) BEFORE accepting. Agent counts via remote APIs can drift, paginate-truncate, or include stale cache.

### Probe 2 — SDK-vs-CLI surface

If the candidate proposes adopting an SDK feature / config flag / env var: verify the **invocation surface** exists in claude-sota:
- Does claude-sota use the SDK or CLI? Check `.claude/hooks/scripts/*.py` + `.claude/settings.json` env block
- Does the candidate's mechanism map to claude-sota's actual mode (interactive vs print-mode vs SDK-managed-agent)?
- If the candidate requires a mode claude-sota doesn't run in, REJECT-for-fit even if SOTA-valid upstream

### Probe 3 — architectural-API

If the candidate proposes a primitive (cache_control, prompt-cache, structured-outputs, batch-API): verify the **API ecosystem match**:
- Anthropic-API primitive vs OpenAI-API primitive vs vendor-neutral OTel
- claude-sota's gpt5.5/codex hooks talk to OpenAI-API endpoints; Anthropic-only primitives don't apply there
- Cross-check before assuming "this Anthropic pattern works on codex"

### Probe 5 — mode-harness-shape

If the candidate proposes adopting a skill/workflow/pattern with operational mode dependencies (HARD-GATE on user interaction, interactive-vs-autonomous mismatch, meta-skill assumptions about sister-harness presence, file-count or size-sprawl orthogonal to existing layout): verify the **operational mode + harness shape match**:
- Does the candidate skill HARD-GATE on interactive user approval? Verify against claude-sota's autonomous /loop mode (incompatible)
- Does the candidate require a sister-skill or sister-harness present in upstream's framework but absent locally? (e.g., Superpowers TDD-for-skills test framework)
- Does verbatim port introduce file count or size disproportionate to existing layer? (e.g., a single skill bringing 7+ files when sibling skills are 1-3 files)
- If ANY mode/harness assumption is unmet, REJECT-FOR-FIT even if SOTA-valid upstream + Axis 1+2+3 PASS

### Probe 4 — plugin-namespace

If the candidate proposes vendoring an artifact from upstream (ECC, codex-plugin-cc, anthropics-cookbook): check **plugin-loaded skill namespace** FIRST:
- `everything-claude-code:<artifact>` exposed via plugin? → DUPLICATE if vendored, REJECT per kiss-dry-yagni Must-Never #4
- `codex:<artifact>` exposed via codex plugin? → DUPLICATE
- `<plugin>:<artifact>` only available as legacy-shim? → still plugin-exposed
- Only proceed with vendoring if the artifact is NOT in any loaded plugin namespace

**Where to check**: the available-skills list injected into agent context via system-reminder (lists every `<plugin>:<skill>` entry). Agents can also `mcp__github__get_file_contents` on the plugin's `marketplace.json` to enumerate exposed commands.

### Probe 6 — supplementary direct-file/registry blockers (FM-09 promotion iter-67)

If the candidate proposes adopting an upstream artifact (skill, MCP server, plugin, library, vendored pattern) whose viability depends on:
- License compatibility (claude-sota is permissive-license-only — MIT / Apache-2.0 / BSD acceptable; AGPLv3 / GPLv3 / SSPL / proprietary REJECT)
- README badge / status banner (archive-status, deprecation notice, "moved to maintenance mode" warning)
- Published-package existence (npm / PyPI / cargo / go-modules registry)
- Build-deps availability (Cargo / GCC / Clang / Python venv requirement)

VERIFY via direct-file/registry probes:
- **LICENSE file read** at upstream root: `cat Z:/repos/deps/<repo>/LICENSE | head -5` — match against permissive-license whitelist
- **README badge inspection**: `rg -n "img.shields.io/badge/license|maintenance|archived|deprecated" Z:/repos/deps/<repo>/README.md`
- **Registry direct-existence probe**: `curl -sS https://registry.npmjs.org/<pkg-encoded>` (`{"error":"Not found"}` = phantom) OR `curl https://pypi.org/pypi/<pkg>/json` (404 = phantom)
- **Build-deps probe**: `which cargo gcc clang` OR check `pyproject.toml` / `package.json` for unsupported dep stack

If ANY direct-file/registry probe surfaces a blocker, REJECT-FOR-FIT even if SOTA-valid upstream + Axis 1+2+3 PASS + Probe 1-5 PASS. The blocker is STRUCTURAL — no operational mitigation exists.
