§2 — Architecture re-think: operator profile is single dev, multi-MAX Claude accounts, unlimited codex usage, Z:-portable Windows install, 12 MCPs already installed. Where did W258 over-shoot (unnecessary complexity) or under-shoot (missed leverage)? Give ≥3 concrete recommendations.

1. Over-shoot: plugin/catalog mass creates context and maintenance drag. Fallback docs admit 26+ plugins and 1,556 SKILL.md across 21 plugins, while user-research warns "2-3 active plugins." W259 should split installed assets into ACTIVE / DORMANT / DISCOVERY-ONLY and enforce an active-plugin budget.

2. Over-shoot: Docker-heavy memory/KG completion is probably too much before MCP health is green. For a single Windows operator, first make the existing 12 MCPs observable, smoke-tested, and restartable. Defer more Graphiti/Qdrant/FalkorDB complexity until current MCP uptime is measured.

3. Under-shoot: unlimited Codex usage is the largest leverage point. Treat Codex as the always-on adversarial verifier, diff reviewer, and CI-rescue lane, not only a T1/T2 ritual. Add a queue of small Codex probes for every candidate repo: install friction, Windows portability, secret surface, and ROI.

4. Under-shoot: Windows portability should be a first-class dimension. Prefer npm/uvx/winget/standalone exe/native PowerShell paths. Penalize bash-only, Docker-only, Linux daemon, symlink, or chmod-centric repos even if their SRA score is high.

5. Under-shoot: 12 MCPs already installed means the next architecture win is routing and policy, not more servers. Add a "tool budget" layer: which MCP is default for docs, code intel, memory, browser, repo search, and when to disable the rest.

6. Over-shoot: grand-catalog adoption percent is a misleading success metric for a single-dev install. Replace "more of catalog touched" with ROI-per-layer and time-to-first-use. A 1k-star tool used daily beats a 50k-star framework that never fires.
