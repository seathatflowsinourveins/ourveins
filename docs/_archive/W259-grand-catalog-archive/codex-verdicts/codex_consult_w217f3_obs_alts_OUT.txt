## How to apply (4-axis probe)

Before declaring an agent's ship-candidate "ready":

### Probe 1 — count-OVER

If the candidate claims a count delta (commit count, file count, line count, star count): verify against authoritative local source (`git log`, `wc -l`, `Glob | wc -l`, `mcp__github__search_repositories` star refresh) BEFORE accepting. Agent counts via remote APIs can drift, paginate-truncate, or include stale cache.

### Probe 2 — SDK-vs-CLI surface

If the candidate proposes adopting an SDK feature / config flag / env var: verify the **invocation surface** exists in claude-sota:
- Does claude-sota use the SDK or CLI? Check `.claude/hooks/scripts/*.py` + `.claude/settings.json` env block
- Does the candidate's mechanism map to claude-sota's actual mode (interactive vs print-mode vs SDK-managed-agent)?
- If the candidate requires a mode claude-sota doesn't run in, REJECT-for-fit even if SOTA-valid upstream

### Probe 3 — architectural-API

If the candidate proposes a primitive (cache_control, prompt-cache, structured-outputs, batch-API): verify the **API ecosystem match**:
- Anthropic-API primitive vs OpenAI-API primitive vs vendor-neutral OTel
- claude-sota's gpt5.5/codex hooks talk to OpenAI-API endpoints; Anthropic-only primitives don't apply there
- Cross-check before assuming "this Anthropic pattern works on codex"

### Probe 5 — mode-harness-shape

If the candidate proposes adopting a skill/workflow/pattern with operational mode dependencies (HARD-GATE on user interaction, interactive-vs-autonomous mismatch, meta-skill assumptions about sister-harness presence, file-count or size-sprawl orthogonal to existing layout): verify the **operational mode + harness shape match**:
- Does the candidate skill HARD-GATE on interactive user approval? Verify against claude-sota's autonomous /loop mode (incompatible)
- Does the candidate require a sister-skill or sister-harness present in upstream's framework but absent locally? (e.g., Superpowers TDD-for-skills test framework)
- Does verbatim port introduce file count or size disproportionate to existing layer? (e.g., a single skill bringing 7+ files when sibling skills are 1-3 files)
- If ANY mode/harness assumption is unmet, REJECT-FOR-FIT even if SOTA-valid upstream + Axis 1+2+3 PASS

### Probe 4 — plugin-namespace

If the candidate proposes vendoring an artifact from upstream (ECC, codex-plugin-cc, anthropics-cookbook): check **plugin-loaded skill namespace** FIRST:
- `everything-claude-code:<artifact>` exposed via plugin? → DUPLICATE if vendored, REJECT per kiss-dry-yagni Must-Never #4
- `codex:<artifact>` exposed via codex plugin? → DUPLICATE
- `<plugin>:<artifact>` only available as legacy-shim? → still plugin-exposed
- Only proceed with vendoring if the artifact is NOT in any loaded plugin namespace

**Where to check**: the available-skills list injected into agent context via system-reminder (lists every `<plugin>:<skill>` entry). Agents can also `mcp__github__get_file_contents` on the plugin's `marketplace.json` to enumerate exposed commands.

### Probe 6 — supplementary direct-file/registry blockers (FM-09 promotion iter-67)

If the candidate proposes adopting an upstream artifact (skill, MCP server, plugin, library, vendored pattern) whose viability depends on:
- License compatibility (claude-sota is permissive-license-only — MIT / Apache-2.0 / BSD acceptable; AGPLv3 / GPLv3 / SSPL / proprietary REJECT)
- README badge / status banner (archive-status, deprecation notice, "moved to maintenance mode" warning)
- Published-package existence (npm / PyPI / cargo / go-modules registry)
- Build-deps availability (Cargo / GCC / Clang / Python venv requirement)

VERIFY via direct-file/registry probes:
- **LICENSE file read** at upstream root: `cat Z:/repos/deps/<repo>/LICENSE | head -5` — match against permissive-license whitelist
- **README badge inspection**: `rg -n "img.shields.io/badge/license|maintenance|archived|deprecated" Z:/repos/deps/<repo>/README.md`
- **Registry direct-existence probe**: `curl -sS https://registry.npmjs.org/<pkg-encoded>` (`{"error":"Not found"}` = phantom) OR `curl https://pypi.org/pypi/<pkg>/json` (404 = phantom)
- **Build-deps probe**: `which cargo gcc clang` OR check `pyproject.toml` / `package.json` for unsupported dep stack

If ANY direct-file/registry probe surfaces a blocker, REJECT-FOR-FIT even if SOTA-valid upstream + Axis 1+2+3 PASS + Probe 1-5 PASS. The blocker is STRUCTURAL — no operational mitigation exists.

### Probe 7 — demand-gate split (NEW 2026-05-03; .a/.b sub-class added 2026-05-05 Wave 27 per Agent E §Issue 1 catch-22)

If the candidate proposes adopting a primitive (MCP / skill / library / tool) that is structurally sound (Probes 1-6 PASS): verify the **harness-side operational driver** BEFORE adoption. #### Probe 7.a — DEMAND-ABSENCE (REJECT-FOR-FIT)

What sss workflow / invocation surface / consumer would route through this primitive TODAY? Verify the 3-clause check:
- Cite a specific path (existing or queued)
- Is the candidate's value proposition met by an EXISTING shipped primitive? (e.g., "graphiti MCP already provides FalkorDB temporal KG access" → dbhub adds no marginal value AS A REPLACEMENT)
- Is the candidate displacing or extending? Displacement requires migration plan; extension requires marginal-value evidence

If NO current/queued workflow AND .b 5-clause check (below) does not survive, REJECT-FOR-FIT.a (demand-absence) — REJECT-decisive.

#### Probe 7.b — DEMAND-CREATES-NEW-WORKFLOW (STUDY-PILOT eligible)

2. **Cited local input/source path**: identify the concrete data, repo path, tool surface, or state file (e.g., `Z:/claude-sota-installed/.claude/state/mcp_overhead_audit.jsonl`)
3. **Wiring path**: name the adapter/ETL/config needed to make the primitive consume the source; if wiring is non-trivial, it is part of the pilot cost
4. **Incumbent comparison**: explain why existing shipped primitives or simpler local commands (`rg`, `jq`, GitNexus, Langfuse MCP, graphiti, mcp-memory, one-off Python scripts) do not already satisfy the use case OR are materially worse
5. **Reversible time-box**: define owner, max pilot cost, 30-day success criterion, and retirement path

**Harness-fit discriminator for REJECT vs STUDY-PILOT outcomes** (renamed from "4-class harness-fit-FAIL discriminator" per Wave 27 codex T1 Q1 prescription — `.b` is non-fail; original Q3 prescription at `.claude/state/codex_consult_axis4_subclass_taxonomy_probe7_demand_absence_OUT.txt:3825-3829` 2026-05-03; .a/.b split per Wave 27 codex T1 verdict at `.claude/state/codex_consult_ship27_3_probe7_demand_creates_OUT.txt` 2026-05-05): use BEFORE classifying a verdict to ensure the right Probe is invoked.

# Convergence Gate — Adopt Only When Pattern Has Converged

# TIER-3 port provenance only: ported from Z:/claude/rules/convergence-gate.md HEAD. Parent CCC retains cycle-N audit evidence; claude-sota authority is the TIER-1/TIER-2 sources cited inside this rule.

## The rule
A new pattern, repo, SDK, or external primitive is ADOPT-NOW only when CONVERGENCE evidence is present. Convergence means the pattern exists independently in multiple authoritative places, not just one. Absent convergence, the default verdict is **REJECT-until-convergence** — not STUDY-PILOT, not "maybe later."

This gate stacks ABOVE the `.claude/skills/sota-research/SKILL.md` 5-row LOAD-BEARING bar (LOCAL — sota-research skill present at `.claude/skills/sota-research/SKILL.md`). It is stricter: the 5-row bar allows STUDY-PILOT on any `[UNKNOWN]`; the convergence gate does not — any missing convergence axis is a REJECT until that axis is satisfied OR the STRONG-PROVENANCE-EXPRESS predicate fires.

## Convergence axes (ALL three required for ADOPT-NOW)

| Axis | Threshold | Evidence shape |
|---|---|---|
| **Independent T1 sources** | ≥3 distinct orgs/repos/papers implementing the pattern | file:line cites in 3 different `Z:/repos/deps/<repo>/` dirs OR 3 different official docs URLs — not 3 pages of the same source |
| **Named T2 practitioners** | ≥2 named practitioners publicly adopting | Recognizable engineers (Karpathy / Simon Willison / Boris Cherny / Anthropic staff / equivalents), with a dated artifact (tweet, blog post, commit, conf talk) citing THIS specific pattern — not generic category endorsement |
| **Stability** | ≥3 months from pattern emergence to evaluation date | first public commit/post ≥90d old; <90d = "new and shiny," re-evaluate after the burn-in period (UNLESS STRONG-PROVENANCE-EXPRESS applies — see §Axis 3 5-band table) |

Any axis failing = REJECT-until-convergence. Verdict line must name the specific missing axis + the exact evidence that would satisfy it.

## Terminology disambiguation

**Convergence-gate Axis 3** = **stability** (age + cpd; quantitative scalar measuring repo/pattern maturity). About: "is this pattern old enough to trust?"

**`.claude/rules/synthesis-layer-verify.md` Subclaim-type discriminator** (UPSTREAM-CLAIM / OPERATIONAL-CLAIM / CATEGORY-CLAIM) = **claim-source classification** (qualitative shape; about what's being verified, not when). About: "which kind of evidence does this claim require?"

Same word "axis" appears in both rules referring to different concepts. Use full names ("Axis 3 stability" vs "subclaim-type discriminator") when ambiguity matters.

## How to apply

Before writing any ADOPT verdict in `reports/sota-*.md` or `reports/*-audit*.md`:

1. **List the 3 T1 sources explicitly**. If you cannot name 3 different `Z:/repos/deps/<repo>/file:line` OR 3 different official docs URLs where the pattern appears independently, the axis fails.
2. **Name the 2 T2 practitioners explicitly with dated artifact**. "Karpathy endorses" without a tweet URL + date is not evidence; it's wishful.
3. **Check the stability clock**. First commit / first public post date — `mcp__github__get_file_contents` on first-commit metadata, or the earliest blog post / paper date. <90d = candidate for STRONG-PROVENANCE-EXPRESS only (see §Axis 3); else fail.
4. **If ANY axis fails**, write `REJECT-until-convergence` as the verdict, with a bullet list specifying exactly what evidence would close each missing axis.
5. **Only then** run the sota-research 5-row bar. The convergence gate is a precondition — passing it doesn't auto-ADOPT, but failing it auto-REJECTS.

## Evaluation methodology — concrete tools per axis

Server-family availability per `.claude/rules/research-protocol.md:52-69` Tool Routing (iter-2 port). Function-level support marked `use-if-available` where the iter-2 routing table didn't independently verify the specific call shape.

### Axis 1 — Independent T1 sources (≥3 distinct)

Parallel enumeration via complementary tools — each catches what the others miss:

| Tool family | Strength | Status |
|---|---|---|
| `mcp__github__search_code` / `mcp__github__get_file_contents` | Exact symbol / import-pattern matches across GitHub | ACTIVE |
| `mcp__octocode__githubSearchCode` | Cross-repo code search with stable query identifiers — substitute: `mcp__github__search_code` | REMOVED (2026-05-03 Round-5d; FM-04 D6 firm) |
| `mcp__deepwiki__read_wiki_structure` + `read_wiki_contents` | AI-generated structured wiki per repo — surfaces patterns not in README keywords | ACTIVE (use-if-available; structure/content calls returned 404 on some repos in prior cycles) |
| `mcp__deepwiki__ask_question` | Repo-level Q&A without reading every file | ACTIVE — verify-only, not sole evidence |
| `mcp__repomix__pack_remote_repository` + `grep_repomix_output` | Cross-file pattern scan inside one repo | ACTIVE |
| `mcp__context7__resolve-library-id` + `query-docs` | Official docs as T1 (when adopting a library) | ACTIVE |
| `mcp__exa__web_search_exa` (category:research paper) | Peer-reviewed papers + named-org blogs as T1 | ACTIVE |
| `mcp__firecrawl__firecrawl_scrape` / `firecrawl_search` | Live-scrape when target is JS-rendered or behind soft paywall | ACTIVE |

**Rule**: at least 3 of these must return positive evidence for the SAME pattern from 3 DIFFERENT orgs/repos/papers. Not 3 different tools on the same source.

### Axis 2 — Named T2 practitioners (≥2 with dated artifact)

| Tool family | Use | Status |
|---|---|---|
| `mcp__exa__web_search_exa` (category:people, full name + pattern) | Find blog posts / talks by named practitioners | ACTIVE |
| `mcp__perplexity__perplexity_search` (recency filter: month/year) | Fresh endorsements — recognizable practitioners mentioning the pattern | ACTIVE |
| `mcp__firecrawl__firecrawl_scrape` on social profiles | Verify a claimed tweet/post actually exists and is dated | ACTIVE |
| `mcp__github__get_me` / search-users / repo collaborator metadata | Employer / org affiliation signals | ACTIVE |
| `mcp__deepwiki__ask_question` on the candidate repo | "Who are the major users or contributors from named orgs?" — triangulate | ACTIVE — use-if-available |

**Mandatory step — WebFetch README + grep practitioners**: GraphQL/`mcp__github__` collaborator metadata is necessary but **not sufficient** for axis 2. Named-practitioner endorsements frequently live in README content (direct quotes, acknowledgments, case studies) rather than repo-collaborator metadata. Before scoring axis 2, ALWAYS:
1. `WebFetch` (or `mcp__firecrawl__firecrawl_scrape`) the README
2. Grep for named-practitioner tokens recognizable in the relevant ecosystem
3. Require URL + date on each citation per the base rule

**Bidirectional**: the README-grep step upgrades verdicts when collaborator-metadata missed a signal AND confirms-REJECT when README also shows zero. Without the README-grep step, canonical repos with direct practitioner endorsements can be scored [UNKNOWN] → REJECT incorrectly.

**Rule**: each claimed practitioner endorsement must have a URL + date. "X tweets about Y" without a link is [UNKNOWN], not T2.

### Axis 3 — Stability (≥3 months first-public-artifact age, scored across 5 bands)

| Tool family | Use | Status |
|---|---|---|
| `mcp__github__get_file_contents` / commit history | `createdAt` / first-commit on the repo — repo age | ACTIVE |
| `mcp__exa__web_search_exa` (date range) | Earliest blog post / paper mentioning the pattern | ACTIVE |
| `mcp__arxiv__search_papers` + `get_abstract` | Paper publication date for research-backed patterns | ACTIVE |

**Rule**: 90 days minimum from EARLIEST public artifact, not from the version you're looking at. A v2.0 release isn't stability evidence if v1.0 was 30 days ago.

**Supplementary signal — commits/day (cpd)**: raw age alone under-specifies stability. A 99-day-old repo shipping 15 commits/day is structurally different from a 99-day-old repo shipping 1 commit/week — the former is still in active iteration, not burn-in. Compute `cpd = total_commits / age_days` alongside age:

| cpd × age band | Classification | Implication |
|---|---|---|
| `cpd < 10` AND `age ≥ 90d` | Stable burn-in | Firm axis-3 PASS |
| `10 ≤ cpd ≤ 20` AND `90d ≤ age ≤ 180d` | Active iteration | Borderline axis-3 — PASS-with-caveat; downgrade to STUDY-PILOT or CONDITIONAL-ADOPT if axis-2 also PARTIAL |
| `cpd > 10` AND `age > 180d` | **Sustained active maintenance** | Firm axis-3 PASS — mature age proves stability AND velocity signals ongoing investment, NOT rewrite churn. Classic shape: high-velocity repos past burn-in (avoid misclassifying as fast-churn anti-pattern) |
| `cpd > 10` AND `age < 100d` | Fast-churn anti-pattern | Treat age-PASS as borderline, expect rewrites, re-audit after +90d |
| **STRONG-PROVENANCE-EXPRESS** (5th band, predicate-gated): `age ≥ 30d` AND axis-1 = official-org maintainership AND axis-2 = named-T2 endorsement OR maintainer-org IS T2-equivalent | **Firm axis-3 PASS — relaxed maturity gate** | When provenance is strong (org-level T1) AND a named-T2 OR org-equivalent endorsement exists, the launch-spike risk that motivates the strict 90-day gate is dominated by maintainer-org commitment. Examples of org-level T1 patterns: vercel-labs / anthropics / openai / getzep / langchain / microsoft / google / facebook-research / google-deepmind / openai-evals / equivalents. The LAUNCH-SPIKE band still applies for `unknown-org + age<90d + cpd>50` — protection holds for the truly anti-pattern cases (solo-org launch with non-permissive license = REJECT-UNTIL-CONVERGENCE unchanged) |

The bands are exhaustive — every candidate falls into exactly one. STRONG-PROVENANCE-EXPRESS is a predicate-gated relaxation, not a default fallback; verify all three predicate clauses (≥30d age, official-org maintainer, named-T2 or org-equivalent endorsement) before applying it.

### Fusion rule (Rider 4 discipline)

No single tool is authoritative. Running any ONE of the above in isolation produces narrow-grep false-negatives (single-tool signal ≠ convergence). The convergence check requires ≥3 distinct tool-types returning compatible evidence — otherwise treat the finding as "one-tool signal," which is not convergence.

Cost discipline: cheap-first. `mcp__github__` calls (cheap, rate-limited) before `mcp__firecrawl__firecrawl_agent` (multi-minute credits). DeepWiki `ask_question` before packing the whole repo with repomix. If 3 cheap signals converge, don't escalate to expensive ones; if they don't converge, ONE expensive confirmatory signal is worth more than three more cheap ones.

## Anti-pattern: retroactive convergence manufacturing

Do not construct convergence evidence after choosing the verdict. The sequence must be: (1) collect convergence evidence → (2) count axes → (3) verdict. Not (1) pick verdict → (2) find supporting cites.

If a candidate looks promising but fails convergence today, the right move is to **queue a re-audit date** (90 days out, or when a named T2 practitioner is spotted adopting it), not lower the gate.
