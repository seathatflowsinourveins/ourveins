## The rule

Code is a liability. Every line has ongoing cost (tests, security patches, dependency updates, onboarding overhead). Deprecation is the discipline of removing code that no longer earns its keep. **Most engineering organizations are good at building things. Few are good at removing them.** This rule addresses the gap.

## When this discipline applies

ANY of these triggers fires this rule:

1. Replacing an old system, API, or library with a new one
2. Sunsetting a feature that's no longer needed
3. Consolidating duplicate implementations (sister to kiss-dry-yagni Must-Never #4)
4. Removing dead code that nobody owns but everybody depends on
5. Planning lifecycle of NEW system at design time ("how would we remove this in 3 years?")
6. Deciding whether to maintain a legacy system or invest in migration

## Hyrum's Law (load-bearing)

> With enough users, every observable behavior becomes depended on — including bugs, timing quirks, and undocumented side effects.

This is why deprecation requires **active migration**, not just announcement. Users can't "just switch" when they depend on behaviors the replacement doesn't replicate.

## The deprecation decision (5-question gate)

Before deprecating ANY surface — code, API, plugin, MCP, hook, rule, agent, skill — answer these in order:

1. **Does this still provide unique value?** → If yes, maintain it. If no, proceed.
2. **How many consumers depend on it?** → Quantify migration scope (`grep -rl "<symbol>"`, `mcp__github__search_code`, etc).
3. **Does a replacement exist?** → If no, build the replacement FIRST. Never deprecate without an alternative. **Replacement readiness gate** (per Wave 82x codex T1 fix-forward F-003 / upstream SKILL.md:71-75): replacement must (a) cover critical use cases of the old system, (b) have documentation + migration guides, AND (c) be proven in production (not just "theoretically better") before deprecation starts.
4. **What's the migration cost per consumer?** → Trivially automated → do it. Manual + high-effort → weigh vs maintenance cost.
5. **What's the ongoing cost of NOT deprecating?** → Security risk + engineer time + opportunity cost of complexity.

## Compulsory vs advisory deprecation

| Type | When to Use | Mechanism |
|---|---|---|
| **Advisory** | Replacement exists, soft-migrate path acceptable | Documentation deprecation note + warning at use site + parallel-deploy + telemetry |
| **Compulsory** | Breaking change required (security, broken contract, blocking next-gen feature) AND maintenance cost or risk justifies forcing migration | Hard removal at version cut OR `@deprecated` + compile error path + migration grace window |

**Default to advisory.** Use compulsory only when maintenance cost or risk justifies forcing migration. Compulsory deprecation requires migration tooling, documentation, and support; a deadline alone is not sufficient. Per Wave 82x codex T1 fix-forward F-002: upstream Osmani SKILL.md:62-65 mandates default-to-advisory + compulsory-with-tooling guardrail.

## Migration patterns (4-stage)

1. **Parallel deploy**: ship new alongside old; both work; no behavior change
2. **Telemetry**: instrument both paths; measure consumer migration via observable signal
3. **Cutover**: when new path adoption exceeds threshold (e.g., 95%), redirect remaining consumers
4. **Removal**: delete old code, dependencies, docs, references — verify ZERO active usage via metrics/logs/dependency analysis (NOT just `rg "<old-symbol>"` text search; per Wave 82x codex T1 fix-forward F-005 / upstream SKILL.md:112-118,201-206); then remove tests + docs + config + deprecation notices

### Churn Rule (load-bearing)

**If you own the surface being deprecated, you own user migration or backward-compatible updates; do not leave consumers to discover the path themselves.** Per Wave 82x codex T1 fix-forward F-004 / upstream SKILL.md:106. This makes the owner responsibility EXPLICIT — distinct from the "Announce-and-leave" anti-pattern below (which describes the failure mode this rule prevents).

## Anti-patterns

- **Announce-and-leave**: emitting `@deprecated` without migration support — Hyrum's Law guarantees nobody migrates. Refuted by §Migration patterns 4-stage active discipline.
- **Hard-remove-without-replacement**: deprecating before a viable migration path exists. Refuted by §The deprecation decision question 3.
- **Maintain-forever**: keeping a legacy system because "users depend on it" without measuring the maintenance cost. Refuted by §The deprecation decision question 5.
- **Speculative-deprecation**: marking code `@deprecated` because "we might replace it someday". This violates kiss-dry-yagni — only deprecate when a real replacement exists. Sister to "speculative ADD" anti-pattern.
- **Deprecate-via-rewrite**: rewriting from scratch + telling users to migrate. Refuted by Joel Spolsky "Things You Should Never Do, Part I" — rewrites lose Hyrum's-Law-encoded knowledge. Migrate IN PLACE when possible.
